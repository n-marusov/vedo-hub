# VEDO Hub Roadmap

> GitHub + Hugging Face for ontologies: social hub, API infrastructure, and LLM generation in one product. Ontologies become living assets — forked, starred, reviewed, cited via DOI, and consumed through API.

## Milestones

- [x] **M0: Foundation & Infrastructure** — Microservices architecture, Docker Compose orchestration, CI/CD pipeline, basic observability (OTEL/Grafana/Prometheus/Loki/Tempo), Keycloak auth, CLI tool (`vedo-cli` with ticket management, secret rotation, guardrail controls)
- [x] **M1: Ontology Core Engine** — Graph browser and navigation (tree of classes, property lists, basic 2D visualization), ontology editor TBox (CRUD for classes, ObjectProperty, DatatypeProperty, annotations), individual management ABox (class instances, property values), Git-like versioning (commits, history, branches, rollback), import/export (Turtle, RDF/XML), REST API for read/write operations, SPARQL endpoint
- [ ] **M2: AI-Assisted Ontology Creation & Document-to-Ontology Extraction** — Low-barrier ontology authoring layer: NL → OWL generation with iterative refinement, AI-assisted class/property completion, relationship hints, ontology templates for common domains, and full document-to-ontology extraction. The document-extractor service (Python) parses uploaded files in 8 formats (MD, TXT, PDF, DOCX, JSON, XML, CSV, XLSX), sends content to an LLM provider for ontology structure generation, presents a user-editable preview, and atomically applies the approved result via gRPC (ApplySequence) to the ontology service with an automatic commit. Supports batch upload of multiple documents with deduplication, custom LLM prompt configuration, and attaching the original file as a commit artifact.
- [ ] **M3: Visual & Natural-Language Query Experience** — Non-specialist query construction on top of the core engine: ontology introspection for dynamic query construction, visual SPARQL/CYPHER drag-n-drop builders, explicit opt-in NL mode for graph queries, unified table/graph result format, CSV/JSON/Turtle export, and saved query library
- [ ] **M4: External LLM Integration & Query Guardrails** — Safe integration layer for external AI clients: MCP server for LLM tools, read-only query enforcement, timeout controls, rate limiting, audit trail, and protected execution paths for generated SPARQL/CYPHER
- [ ] **M5: MVP UX, Accessibility & Governance** — WCAG MVP keyboard/screen-reader scenarios, accessible auth/navigation/editor/versioning/publishing flows, safe destructive actions and data-loss prevention, critical error feedback and degraded-mode UX, GitLab-like organization membership/permissions, JWT/API auth, OpenAPI documentation, BOLA/BFLA authorization regression gates, parser/query fuzz gates, SCA/SBOM gates, and write idempotency for API operations
- [ ] **M6: Collaboration & Social Hub** — Entity comments, project comment feed, mention notifications, comment visibility by access rights, Merge Request review workflow with semantic diff, public author profiles, stars, forks, issues with templates, GitHub-style Pull Requests, DOI-ready publication metadata, CI/CD publication automation for ontology changes, community forum, public roadmap with voting, and opt-in usage telemetry
- [ ] **M7: CLI Administration, Operations & Support** — `vedo-cli` production operations: scheduled backup/restore with verify, immutable backup policy, Neo4j/PostgreSQL migrations with rollback and integrity checks, air-gapped installation package preparation, ontology transfer/import/export between environments, `diff` of two ontology versions, incident diagnosis by `trace_id` with LLM-assisted recommendations, support tickets, in-app feedback widget with metadata, NPS collection, knowledge base (Antora docs), support SLA/escalation, and public status page
- [ ] **M8: API as Infrastructure Layer** — Unified root API, REST versioning and backward compatibility policy, GraphQL/SPARQL split, managed SPARQL and CYPHER endpoints, semantic search across public ontologies, CRUD ontology operations via API, webhooks for change notifications and CI/CD automation, API coverage/compatibility gates, on-premise LTS API support, and saved SPARQL query sharing
- [ ] **M9: Publishing, Import/Export & Reporting** — Snapshot publishing pipeline, public read-only browse API/UI, public ontology access model, dedicated publication storage, public full-text search and 2D/3D navigation, DOI registration for published ontologies, XLSX import/export for ontologies and individuals, DOCX export, configurable import form templates, ontology reports, and import/export safety UX
- [ ] **M10: Advanced Ontology Quality & Analytics** — Complex OWL constructs (class equivalence, intersection, union, complement), property characteristics (transitivity, symmetry, functionality, inverse), visual graph editor with drag-n-drop relationship editing, SHACL validation, visual data-quality rules, deduplication support, OWL consistency validation via API (semantic linter at PR), entity resolution/link discovery via API, ontology complexity trends, feedback analytics, and opt-in usage telemetry
- [ ] **M11: Enterprise, Resilience & Compliance** — SaaS/on-premise/air-gapped deployment tiers, deployment geography and data residency, environment configuration, control-plane isolation, edge/region failover, availability and recovery SLOs (RTO/RPO), restore and decommission drills, secure erase, account-closure/decommission export and retention, privileged access with JIT/PAM and MFA for critical CLI operations, emergency policy disable/kill switch, support metadata isolation, staged rollout with auto-rollback, pre-prod release gates, and UAT/e2e release evidence
- [ ] **M12: Scale, Intelligence & Marketplace** — Large-graph visualization (WebGL, virtualization), advanced ontology analytics (hierarchy depth, branching factor, data coverage), Enterprise tier with dedicated API endpoints and SLA, GitHub/GitLab sync plugins, LLM generation via API (NL → OWL programmatically), fork/versioning via API, author sponsoring (GitHub Sponsors-style), and partner commissions for popular ontologies

## Roadmap Notes

- **Vision coverage:** M1–M12 explicitly cover all 16 functional domains from `specs/vision.md`: F1/F2/F3/F4 in M1, F5 in M6, F6/F16 in M5/M8/M12, F7 in M10/M12, F8 in M1/M9, F9 in M7/M11, F10/F15 in M3/M4/M8, F11 in M9, F12 in M7/M10/M11, F13 in M6/M12, F14 (F14.1–F14.8) in M2/M10/M12, and F15/F16 across M3/M4/M8/M12.
- **AI-first strategy:** M2–M4 are placed immediately after the core engine (M1) because VEDO targets a broad audience beyond ontology engineers. The sequence first lowers authoring barriers with AI generation/templates (M2), then gives non-specialists visual and natural-language query tools (M3), and only then exposes safe external LLM/MCP integration with execution guardrails (M4).
- **MVP alignment:** The MVP scope from `specs/vision.md` section 2.5 is covered across M1–M5, with AI/onboarding split into creation, query UX, and guarded external integration (M2–M4), followed by UX/governance (M5), because accessibility for non-specialist users requires both intuitive AI tooling and a polished, secure, WCAG-compliant interface.
- **Post-MVP alignment:** Vision section 2.6 defines four post-MVP stages. **Этап 2** (AI assistant, NL→OWL, visual constructors, templates, MCP server, query library) maps to M2–M4. **Этап 3** (social hub, collaboration, forum, DOI, telemetry) maps to M6/M9. **Этап 4** (API infrastructure, OWL validation, entity resolution, LLM via API, webhooks) maps to M8/M10. **Этап 5** (Enterprise, scale, GitHub/GitLab sync, sponsoring, commissions) maps to M11–M12.
- **Use case and user story coverage:** The roadmap covers the UC/US domains: `browse`, `editor`, `abox`, `git`, `team`, `api`, `admin`, `diagnostics`, `io`, `metrics`, `support`, and `a11y`. Dedicated coverage was added for planned UC/US around accessibility, API auth/docs/webhooks, air-gapped operations, support/status/roadmap/community, publishing, XLSX/DOCX/forms/reports, metrics, and feedback analytics.
- **Requirements and ADR alignment:** Milestones reflect the requirement/ADR groups for API compatibility/versioning/idempotency, SPARQL/CYPHER/MCP and NL opt-in, storage/versioning/migration/rollback, deployment strategy and integrity, air-gapped deployment, observability and incident response, authorization/security gates, privileged CLI access, WCAG/accessibility, UI safety/recovery/degraded mode, support SLA, decommission/retention, and microservices/polyglot stack decisions.
- **Architectural boundary:** The roadmap preserves the architecture decision to use microservices in a monorepo, API-first service contracts, API Gateway as the frontend/backend entry point, service-owned data stores, OpenTelemetry trace propagation, RabbitMQ for async workflows, and `vedo-cli` as the operator boundary.
- **Scope constraint:** Real-time co-editing with pessimistic node locks is intentionally not planned; collaboration is modeled through branches, comments, Merge Requests, reviews, notifications, and semantic diff, matching the vision constraints.
- **Continuous NFRs:** Performance targets (up to 1M axioms, p95/p99 latency, export time), observability, security gates, API compatibility, accessibility, rollout safety, documentation/localization, and release-quality evidence apply continuously across all milestones rather than as one-off deliverables.
- Milestones are ordered by dependency: core engine first, then AI-assisted ontology creation, visual/NL query experience, guarded external LLM integration, UX/governance, collaboration/social, operations/support, API infrastructure, publishing/exchange, ontology quality, enterprise resilience, and scale/marketplace.
