# VEDO Hub Roadmap

> GitHub + Hugging Face for ontologies: a team platform for creating, governing, versioning, and AI-assisted ontology projects through Web UI, REST API, and MCP.

## Milestones

## Roadmap Notes

- **MVP source of truth:** MVP scope is governed by `specs/vision.md` section 2.5. The MVP is intentionally limited to the demonstrable chain: посадочная страница → группа → проект → участники → демо-проект (fork)/документ → генерация онтологии → TBox/ABox редактирование → class/TBox/ABox навигация → commit/history/basic Semantic Diff → REST API/MCP.
- **Continuous numbering:** Milestones use a single continuous `M*` sequence. Former `M2.1` is now `M3`; former `M2.5` is now `M4`. Completed statuses and completed dates were preserved.
- **Organization model:** The GitLab-like group/project/member model is part of MVP, not a later enterprise feature. It defines ownership, visibility, RBAC inheritance, and audit boundaries for all ontology work.
- **Document AI priority:** Document-to-ontology generation is a high-priority MVP capability because the target user often starts from real `DOCX`, text `PDF`, `XLSX`, `JSON`, `MD`, or `TXT` artifacts rather than from hand-written OWL/RDF. M2 completed the backend/API and baseline upload→preview→apply path; missing GUI entry points for NL→OWL, refinement, and AI suggestions are tracked as M4/M5 wiring gaps. MVP excludes OCR, encrypted-document password handling, custom prompts, advanced merged-source deduplication, and template-as-document-context.
- **Demos in MVP:** 5 demo projects in `VEDO Demos` group serve as onboarding accelerators for the editor. Users fork demo projects via `POST /api/v1/projects/{id}/fork` — fork replaces the former `Ontology Template` concept (ADR-DES.PROCESS.templates-via-forks). Fork is also the base mechanism for Social Hub (F13.1). Demo project marketplace, custom public projects as demos, and merge-upstream-changes are post-MVP.
- **Navigation split:** MVP must not collapse class hierarchy and graph visualization into one view. It needs separate Class Hierarchy View, TBox Graph View, and ABox Graph View (tracked as M5 checkbox).
- **E2E test evidence (verified 2026-08-02):** API E2E — **66/66 pass**. GUI — **119 pass / 78 skip / 0 fail** (78 skips are milestone-annotated: post-MVP features M8-M13 + timing-dependent loading tests; AI completion/property/refinement specs un-skipped — features implemented in M4 Д1-Д3). Wired GUI (`*-wired.spec.ts`, excluded from default GUI config) — 15/15 pass. Fork security tests GREEN: `tests/security/authorization/fork_bola_test.go` 7/7. RBAC security integration suite (authorization module) **runnable** against the test stack — 45/49 (4 RED = TC-001/003/011/012 BOLA «never 404» policy, tracked to M7 authorization regression scope, not papered over).
- **Versioning integration tests (verified 2026-08-02):** GREEN — `transactional_integration_test.rs` 5/5; `run_manual_migrations` serialized via `pg_advisory_lock` (key 787_896_734) + per-binary `OnceCell` guard; `make test-versioning-fast` uses dedicated `vedo_versioning_test` DB (create-if-missing) with correct creds/port.
- **metrics-service (verified 2026-08-02):** ✅ Healthy — Prometheus counter registration made idempotent (`_metric()` dedup guard); 5 pytest tests (`tests/test_metrics.py`: health, ready, root identity, dedup guard, metrics payload). MetricsPage GUI e2e (4 tests) skipped — analytics/diagnostics dashboards are M13, milestone-annotated.
- **merge blocking (verified 2026-08-02):** ✅ Implemented — 409 VER-MERGE-CONFLICT guard in `BranchRepository::merge_branches` (check before write); unit + integration tests green. M5 item closed; unblocks M10 invariant enforcement.
- **SPARQL audit (verified 2026-08-02):** ✅ Implemented — ontology-service `audit.rs` structured JSON audit per query (trace_id, user, dialect, query, LIMIT, execution_time_ms, status), incl. rejected/mutation. M5 item closed; prerequisite for M6 MCP audit.
- **Public landing (verified 2026-08-02):** ✅ Live — `publish-browse-ui` serves hero/demos/roles/metrics/footer per ADR-DES.UI.public-landing-architecture; 9 tests; E2E smoke verified. F11.1 closed — first element of MVP demo chain.
- **Public landing page in MVP:** Минимальный публичный лендинг (hero, витрина демо-онтологий, кликабельный граф, email CTA) входит в MVP как F11.1 в составе функции F11 «Публикация онтологий» (vision.md §2.2, §2.5). Это лёгкая витрина — НЕ полноценный Public Browse 1.0 (поиск, DOI, visibility model), который остаётся в M11.
- **Semantic Diff boundary:** Basic Semantic Diff is implemented — entity-level diff (classes, properties, individuals) with summary counts via `GET /api/v1/projects/{pid}/repository/commits/{sha}/diff`. Visual graph diff, reasoning-aware diff, manual conflict resolution, and Merge/Pull Request review workflows are post-MVP.
- **MCP boundary:** A minimal MCP server is part of MVP and must share RBAC, audit logging, and safety limits with REST/UI operations. Advanced agentic workflows, auto-merge, document extraction through MCP, and admin operations through MCP are post-MVP.
- **Import/export boundary:** OWL/RDF import/export is deliberately deferred after MVP. The MVP focuses on demo projects, document generation, and fork mechanics as the primary onboarding paths.
- **Stub policy:** Future functions should appear as disabled/read-only GUI stubs and documented API stubs returning `501 Not Implemented` or marked with `x-vedo-status: planned`. Stubs stabilize navigation and API contracts without expanding MVP implementation scope.
- **1.0 direction:** Version 1.0 turns the MVP into a product by expanding query UX, document AI, collaboration/review workflows, import/export/publishing, validation/reasoning, operations, support, and analytics.
- **Scope constraint:** Real-time co-editing with pessimistic node locks is not a near-term roadmap driver; collaboration is primarily modeled through projects, roles, comments, branches, Semantic Diff, and later Merge/Pull Request workflows.
- **Foundational ADRs (pre-M5):** Three architectural decisions formalized in M5 as prerequisites for later milestones: ADR-DES.API.write-path-invariant (no direct writes to ontology — only branch→commit→MR→merge), ADR-DES.API.rest-gitlab-alignment (REST paths nested under /projects/{pid}/ with :ref= parameter), ADR-DES.INFRA.publishing-extension (CQRS serving layer, binary visibility, maintainer gate). Implementation deferred to M10 (invariant enforcement) and M11 (publishing pipeline). Code guardrails (deprecation headers, 501 stubs) applied now.
- **REST API GitLab Alignment Migration:** The migration of legacy flat REST paths (`/api/v1/ontologies/*`, `/api/v1/versioning/*`) to the GitLab-aligned project-scoped structure (`/projects/{pid}/repository/*`, `/merge_requests`, `/releases`, `/protected_branches`) is a cross-cutting track executed inside **M10** (versioning + MR + branch protection + OpenAPI) and **M11** (publishing + ontology/AI CRUD + GraphQL boundary + clients). There is no separate "Phase B" milestone — the concrete task breakdown and endpoint mapping live in plan `feature-rest-api-realignment-adrs.md` (Phase 9 implements the versioning track now; remaining tracks itemized in section "REST API GitLab Alignment Migration").
- **Deprecated-path removal phase (after migration):** Legacy paths carry `Deprecation: true` + `Sunset` headers since M5 guardrails. Removal is a **distinct closing phase of the migration**, executed after each track's consumers have fully switched to the project-scoped surface (frontend API clients, vedo-cli, E2E/security path tables, OpenAPI). Concretely: (1) **M10 close** — remove `/api/v1/versioning/*` routes and their OpenAPI definitions once the frontend VersioningPage and E2E tests use `/projects/{pid}/repository/*` only; (2) **M11 close** — remove `/api/v1/ontologies/*` (CRUD + AI/document + comments) routes and OpenAPI definitions once consumers migrate. The `versioningDeprecated`/`ontologyDeprecated` route groups in api-gateway (`routes.go`) are deleted in this phase, along with the `deprecationSunset()` middleware wiring.
- **Continuous NFRs:** Performance, security, observability, accessibility, API documentation, localization, and release evidence apply continuously across milestones rather than as one-off deliverables.
