# Undefined Docker image variables in docker.mk causing build failure

**Date:** 2026-07-22 20:10
**Files:** src/build/docker.mk
**Severity:** high

## Problem

`make docker-build` failed with:
```
D:/Projects/vedo-hub/src/build/docker.mk:12: warning: undefined variable 'CARGO_CHEF_IMAGE'
D:/Projects/vedo-hub/src/build/docker.mk:12: warning: undefined variable 'RUST_BASE_IMAGE'
D:/Projects/vedo-hub/src/build/docker.mk:12: warning: undefined variable 'RUST_RUNTIME_IMAGE'
...
ERROR: failed to build: failed to solve: base name (${RUST_BASE_IMAGE}) should not be blank
```

The Docker build passed `--build-arg VAR=$(VAR)` for variables that were never defined. Docker received empty build-arg values, which overrode the Dockerfile's `ARG VAR=default` defaults with empty strings. This made the `FROM` instruction blank.

## Root Cause

1. `docker.mk` included `$(ROOT)/.env` (= `src/.env`) for variable definitions, but `src/.env` only contained Docker Compose port variables — not Docker image tags.
2. Make was configured with `--warn-undefined-variables` (from the root Makefile) but no `?=` fallback defaults were set.
3. Build context was `src/` while `docker-compose.yml` uses project root as context — two different build contexts for the same Dockerfiles.
4. `SERVICE_DIR` was set to absolute Windows paths (`D:/.../services/ontology-service`) or broken relative paths, but Docker COPY only works with paths relative to the build context.
5. Go build used `SERVICE_DIR=$$dir` (service-specific dir) but Dockerfile.go expects the parent directory (`src/services`) — COPY paths had double-directory nesting.
6. `--build-arg` names for Python (`PYTHON_BASE_IMAGE`) and TypeScript (`NODE_BASE_IMAGE`) didn't match Dockerfile `ARG` names (`PYTHON_IMAGE`, `NODE_IMAGE`).

## Solution

1. Added `?=` defaults for all Docker image variables (`CARGO_CHEF_IMAGE`, `RUST_BASE_IMAGE`, `RUST_RUNTIME_IMAGE`, `GO_BASE_IMAGE`, `GO_RUNTIME_IMAGE`, `PYTHON_IMAGE`, `PYTHON_RUNTIME_IMAGE`, `NODE_IMAGE`, `NGINX_IMAGE`).
2. Unified build context to project root (`PROJECT_ROOT := $(realpath $(ROOT)/..)`) — consistent with `docker-compose.yml`.
3. Fixed all `SERVICE_DIR` paths to be relative to project root with `src/` prefix, matching compose file semantics.
4. Fixed Go `docker-build-go`: changed `SERVICE_DIR=$$dir` → `SERVICE_DIR=src/services`, added `case` filter to skip `cli` and sub-packages (`services/*/*`), added `vendor/` existence check for incomplete services (e.g. `support-service`).
5. Fixed `--build-arg` names: `PYTHON_BASE_IMAGE` → `PYTHON_IMAGE`, `NODE_BASE_IMAGE` → `NODE_IMAGE`.
6. Rust: skip `shared` library crate in build loop. Python: compute `SERVICE_DIR` from service basename.

## Prevention

- Variables used in `--build-arg` should always have `?=` fallback defaults.
- Docker build context must be consistent between `make` and `docker compose` — project root is the standard.
- When a Make variable name differs from the Dockerfile `ARG` name, the `--build-arg` has no effect.
- Go `SERVICE_DIR` must point to the parent of all service directories (`src/services`), not the individual service — the Dockerfile appends `/${BINARY_NAME}`.
- Filter non-service modules (`cli`, sub-packages) explicitly in build loops.
- Go services without `vendor/` must be skipped or populated via `go mod vendor` before Docker build.
- CI should run `make docker-build-<lang>` to catch build regressions early.
