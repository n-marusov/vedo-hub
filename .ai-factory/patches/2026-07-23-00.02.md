# Keycloak auth regression in DEV — KC_HOSTNAME override and JWT claims mismatch

**Date:** 2026-07-23 00:02
**Files:** .env.dev, src/services/api-gateway/auth/auth.go
**Severity:** critical

## Problem

KeyCloak authorization stopped working in the DEV environment — the frontend OIDC
login flow either failed to complete (redirect to a non-existent domain) or returned
an empty user identity (empty `user_id` and missing roles) after token validation.

The problem was previously fixed by commits:
- `d0891bc` (frontend OIDC config alignment)
- `821a311` (Keycloak persistence + KC_HOSTNAME=localhost + JWT introspection)
- `a0604d1` (JWT verification + role overrides)

But two regressions undid the fixes.

## Root Cause

**Regression 1 — KC_HOSTNAME.** The docker-compose.yml fixes from `821a311` set
`KC_HOSTNAME=${KC_HOSTNAME:-localhost}` so the default is `localhost`. But `.env.dev`
contained `KC_HOSTNAME=auth.vedo.dev` which overrode the docker-compose default.
The domain `auth.vedo.dev` does not resolve in the dev environment, causing:

1. After OIDC login, Keycloak redirected the browser to `http://auth.vedo.dev:8180/...`
   which could not be reached.
2. Keycloak minted JWTs with `iss=http://auth.vedo.dev:8180/realms/vedo-core`
   instead of `iss=http://localhost:8180/realms/vedo-core`.

The `.env.dev` file was not tracked in git (gitignored), so the regression was
invisible to CI and code review. It was likely introduced manually or by a local
environment setup script targeting a planned production domain.

**Regression 2 — JWT claims mismatch.** The API gateway's `AuthClaims` struct
expected `user_id`, `tenant_id`, and `roles` at the JWT top level, but Keycloak
(OIDC standard) puts:
- `sub` instead of `user_id`
- `realm_access.roles` instead of `roles`

The gateway used local JWT validation (commit `a0604d1`) and never called the
auth-service's introspection endpoint (which correctly parsed `realm_access.roles`
from Keycloak's RFC 7662 response). This meant even a valid JWT yielded an empty
`userID` and no roles, causing `resolveEffectiveRole([])` to fall back to Viewer
(weight 0) with an empty user context propagated downstream.

## Solution

**Fix 1 — .env.dev:**
- Changed `KC_HOSTNAME=auth.vedo.dev` to `KC_HOSTNAME=localhost`
- Added explicit `KEYCLOAK_JWKS_URL=http://keycloak:8080/realms/vedo-core/protocol/openid-connect/certs`
  to document the JWKS endpoint used by the API gateway inside Docker

**Fix 2 — auth.go AuthClaims:**
- Added `RealmAccess` nested struct (`json:"realm_access"`) with a `Roles` field
  to capture Keycloak's standard OIDC role claim shape
- Added fallback: when `claims.UserID` is empty, use `token.Claims.GetSubject()` to
  extract the `sub` claim (Keycloak's standard user identifier)
- Added merge logic: combine top-level `roles` with `realm_access.roles`, deduplicating
  entries so both custom mappers and standard OIDC roles coexist

## Prevention

- `.env.dev` should be tracked in git (or at least `.env.dev.example` should exist)
  with comments explaining each variable's purpose, so domain-specific overrides
  are visible in code review
- When Keycloak realm configuration uses standard OIDC claim names (`sub`,
  `realm_access.roles`), the JWT validation code must handle them — either via
  custom protocol mappers in the realm or via the `AuthClaims` struct
- Add a CI check that runs `docker compose --env-file .env.dev config` and
  validates the resolved KEYCLOAK_JWKS_URL is reachable or the default is used
- Run `go test ./auth/...` in CI after any AuthClaims struct changes — the
  `TestProperty_MissingRoleClaimDefaultsViewer` test covers the empty-role default
  but does not cover `realm_access.roles` parsing (a new test should cover this)
