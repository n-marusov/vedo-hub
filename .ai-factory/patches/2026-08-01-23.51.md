# Localize all remaining page controls (17 pages + locale parity fix)

**Date:** 2026-08-01 23:51
**Files:** apps/services/frontend/src/pages/*.vue (17 files), src/locales/en.json, src/locales/ru.json, vitest.setup.ts
**Severity:** medium

## Problem

After the shell (App.vue) was localized, all page-level UI controls were
still hardcoded in English: dashboard headings/buttons, login page, members
table and remove dialog, metrics KPIs, comments composer, deployments,
merge requests tabs, SPARQL/SHACL builders, validation report, versioning
tabs, public ontology view, and the ontology workspace toolbar + AI import
panel.

Additionally `t("common.retry")` was referenced in several pages but the
key did not exist in the locale files (only `groups.retry` /
`projects.retry` did) — the button rendered the raw key `common.retry`.

## Root Cause

1. Pages were written before i18n existed or never wired to it — only
   `GroupsPage`, `ProjectsPage`, `CreateGroupPage`, `CreateProjectPage`,
   `GroupDetailPage` used `useI18n`.
2. No key-parity gate existed, so a missing key silently fell back to the
   raw key string in the UI (visible regression: "common.retry" button).
3. Component tests rendered pages with no loaded locale, so `t()` returned
   raw keys; any test asserting visible English text failed once pages
   started using `t()`.

## Solution

- Wired `useI18n` + `t()` into all 17 remaining pages, translating UI
  chrome only (buttons, headings, placeholders, aria-labels, empty/error
  states, relative-time strings). Backend/API data (widget titles, activity
  feed text, demo project names) is intentionally left untranslated — it is
  server-provided content, not frontend UI.
- Made relative-time and locale-date formatting locale-aware
  (`formatTimeAgo` via `t("...time_ago_m")`, `toLocaleDateString(locale)`).
- Added 179 new keys to `ru.json`/`en.json` with full parity (305 keys each)
  and added the missing `common.retry`.
- Added a key-parity verification: `node -e` script comparing key sets of
  both locale files (must be empty both ways).
- Preloaded the English locale in `vitest.setup.ts`
  (`await useI18n().setLocale("en")`) so component tests render real
  translated text instead of raw keys; use a relative import because the
  file lives outside `src/` and the `@` alias is not resolved there by the
  TS config.

## Prevention

- Before referencing a `t("some.key")`, verify the key exists in BOTH
  locale files (missing keys render as raw key strings — silent failure).
- After bulk key additions, run a parity check between `ru.json` and
  `en.json` key sets.
- Prefer a shared test-setup locale preload over per-test setLocale calls
  so page-level component tests assert real translated strings.
- Keep localization to frontend UI chrome; document that API-provided data
  is not localized client-side.
