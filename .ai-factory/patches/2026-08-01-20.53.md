# Dev environment: 401 on group creation — self-signed JWT minted by Makefile

**Date:** 2026-08-01 20:53
**Files:**

- `deploy/docker-compose.dev.yml` (new)
- `deploy/dev-jwt/gen-dev-jwt.js` (new)

**Severity:** medium

## Problem

In the dev environment, `POST /api/v1/groups` (group creation) returned
`401 Unauthorized`. Skipping auth (`VEDO_SKIP_AUTH=true`) was not sufficient —
the frontend sent a fake `"skip-auth-token"` (or nothing) in the
`Authorization` header, which the API Gateway rejected because it is not a
validly-signed JWT.

## Root Cause

Two compounding issues:

1. **SKIP_AUTH never populated a valid JWT for API calls.** `session.ts`
   `getSession()` returned a mock session with `accessToken: "skip-auth-token"`
   in SKIP_AUTH mode, but `localStorage.vedo-jwt-token` (the storage backend
   read by every Apollo/Axios interceptor) was only written by `saveSession()`,
   which runs exclusively on the Keycloak callback path. So in SKIP_AUTH mode
   the API clients had no valid Bearer token and the gateway answered 401.
   The router guard passed (mock session) so the failure surfaced only on the
   actual API call — "skip auth is not enough".
2. **Dev gateway validated against Keycloak JWKS only.** The base
   `docker-compose.yml` configures `KEYCLOAK_JWKS_URL`, so only tokens signed
   by Keycloak were accepted. There was no dev path to mint a locally
   acceptable token.

## Solution

Mirrored the proven E2E mechanism (`docker-compose.test.yml` +
`global-setup.ts`) for dev:

1. **`deploy/docker-compose.dev.yml`** (new dev overlay): sets
   `JWT_DEV_PUBLIC_KEY_PEM` (the e2e test public key) on the api-gateway —
   highest priority in `keyfunc.go` — so it accepts self-signed RS256 tokens;
   sets `BUILD_PROFILE: dev` + `VEDO_SKIP_AUTH=true` on the frontend so the
   SKIP_AUTH runtime branches are kept in the bundle.
2. **`deploy/dev-jwt/gen-dev-jwt.js`** (new): host-side JWT minting at
   `make docker-up` time (node + jsonwebtoken + `tests/e2e/scripts/test-jwt-key.pem`,
   RS256, Owner claims, 24h expiry) — the dev analogue of the e2e
   `global-setup.ts`.
3. **`Makefile`**: `ENV=dev` now selects the dev overlay; `docker-up` mints the
   JWT and passes it as `VEDO_DEV_JWT_TOKEN` to the frontend container.
4. **`docker-entrypoint.sh`**: when `VEDO_SKIP_AUTH=true` and
   `VEDO_DEV_JWT_TOKEN` is present, copies the token into `config.js` as
   `DEV_JWT_TOKEN`. The existing production security gate (refuse to boot with
   SKIP_AUTH in a production env) prevents this from leaking to production.
5. **`session.ts`**: in SKIP_AUTH mode, uses `window.__VEDO_CONFIG__.DEV_JWT_TOKEN`
   (when present) to build a real session and `saveSession()` writes it to
   `localStorage.vedo-jwt-token` → API calls carry a Gateway-accepted Bearer
   token → group creation succeeds (201).

## Prevention

- **Never write a fake "skip-auth-token" that bypasses only the router.** The
  API Gateway is the real auth boundary; any dev/test "skip" mode must still
  present a token the gateway can verify.
- **When a storage backend is written by only one code path, trace ALL
  consumers.** `saveSession()` wrote both storages, but SKIP_AUTH mode never
  called it — the mismatch was invisible until an API call failed.
- **Mirror the E2E token mechanism for dev** (same keypair, host-side
  minting, gateway accepts via `JWT_DEV_PUBLIC_KEY_PEM`) instead of inventing
  a separate key or embedding keys in images.
- **Keep private keys out of containers**: the signing key stays on the host
  (used by the Makefile step); only the minted token enters the frontend.
