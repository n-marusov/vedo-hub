# JWT token not synced to localStorage after Keycloak login

**Date:** 2026-07-21 12:15
**Files:** src/services/frontend/src/auth/session.ts
**Severity:** high

## Problem

After a successful Keycloak OIDC login, all GraphQL and REST API requests returned `UNAUTHENTICATED` (HTTP 401). The frontend logged repeated `auth.denied` errors for every request to `/api/v1/graphql`.

## Root Cause

The auth flow had a mismatch between write and read storage locations:

- **Write path:** `keycloak.ts::handleCallback()` → `session.ts::saveSession()` stored the UserSession in `sessionStorage.vedo_session`
- **Read paths:** Apollo Client (`apollo/client.ts`), Axios interceptors (`api/ai.ts`, `api/extraction.ts`), and user info (`composables/useCurrentUser.ts`) all read the raw JWT token from `localStorage.getItem("vedo-jwt-token")`

No code ever wrote to `localStorage.vedo-jwt-token`. The Playwright E2E tests worked because they explicitly set both storage locations via `addInitScript()`, but the production login flow was broken.

## Solution

Added a single `localStorage.setItem('vedo-jwt-token', session.accessToken)` call in `session.ts::saveSession()`, and a corresponding `localStorage.removeItem('vedo-jwt-token')` in `session.ts::logout()`. This ensures that whenever a session is saved or cleared, both storage backends stay in sync.

## Prevention

- When a frontend auth flow stores tokens, verify that ALL consumers (Apollo Client, Axios interceptors, auth guards) can access the stored token.
- When adding E2E test auth helpers that set both `sessionStorage` and `localStorage`, treat the dual-set as a signal that the production flow must do the same.
- Code review checklist: for any `localStorage.getItem("vedo-jwt-token")` call, verify there's a corresponding write somewhere in the login flow.
