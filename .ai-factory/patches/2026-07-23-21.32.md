# Fix: GET /api/v1/groups incorrectly requires Owner role (FORBIDDEN_ADMIN_ONLY)

**Date:** 2026-07-23 21:32
**Files:** src/services/api-gateway/auth/auth.go (isAdminEndpoint)
**Severity:** high

## Problem

`GET /api/v1/groups` returned `403 Forbidden` with `{"error":{"code":"FORBIDDEN_ADMIN_ONLY","message":"Admin access required"}}` for non-Owner users. This violated the GitLab-like organization access model (REQ-NFR.SECURITY.organization-access-model), which defines roles Viewer/Editor/Maintainer/Owner — not "Admin" — and expects read access to be available to all authenticated users.

## Root Cause

The `isAdminEndpoint()` function in `auth.go` used a broad `strings.Contains(path, "/groups") || strings.Contains(path, "/projects")` catch-all (line 365), marking ALL paths containing `/groups` or `/projects` as admin-only (required role level 3 = Owner). This included read endpoints like `GET /api/v1/groups`, `GET /api/v1/projects`, etc.

The `methodRequiredLevel()` function calls `isAdminEndpoint()` first, returning level 3 for any admin path regardless of HTTP method. A Viewer (level 0) or Editor (level 1) could never pass this gate, causing the 403.

Additionally, `strings.Contains(path, "/policies")` had the same issue — `GET /api/v1/projects/:id/policies` also required Owner, blocking any non-Owner from viewing policies.

The problem was that the function conflated "this path is for org management" with "this path requires Owner role". CRUD operations on groups/projects include read endpoints that should be accessible to any authenticated user.

## Solution

Removed both the `/groups`/`/projects` catch-all and the `/policies` catch-all from `isAdminEndpoint()`. The fine-grained authorization for mutation operations (create/update/delete) is delegated to the auth-service at the gRPC level, which enforces proper Owner/role checks.

With this change:
- `GET /api/v1/groups` → `methodRequiredLevel` returns 0 (Viewer) — accessible to all authenticated users
- `GET /api/v1/projects` → `methodRequiredLevel` returns 0 (Viewer) — accessible to all authenticated users
- `GET /api/v1/projects/:id/policies` → `methodRequiredLevel` returns 0 (Viewer) — accessible to all authenticated users
- `POST /api/v1/groups` → `methodRequiredLevel` returns 1 (Editor) — coarse gate, auth-service enforces Owner
- `PUT/DELETE` on groups/projects → `methodRequiredLevel` returns 2 (Maintainer) — coarse gate, auth-service enforces Owner
- `POST/DELETE` on policies → coarse gate, auth-service enforces Owner

## Prevention

- When classifying endpoints as "admin-only" in coarse BFLA gates, consider the full spectrum of HTTP methods. Read operations (GET) should not require Owner unless the data itself is admin-only.
- Auth-service gRPC layer already enforces proper role checks — the API Gateway BFLA gate is defense-in-depth, not the primary authorization mechanism.
