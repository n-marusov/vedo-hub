# Port mapping fix — Makefile ENV default and publisher-service port conflict

**Date:** 2026-07-22 19:00
**Files:** src/Makefile
**Severity:** medium

## Problem

Running `make docker-up` without `ENV=dev` caused two issues:

1. **Warning**: `Makefile:188: warning: undefined variable 'ENV'` — because `MAKEFLAGS += --warn-undefined-variables` is enabled and `ENV` had no default value
2. **Port conflict**: Without `--env-file`, Docker Compose used default port values from `docker-compose.yml`. The publisher-service attempted to bind to `0.0.0.0:9005` (its default gRPC port), which failed with: `Bind for 0.0.0.0:9005 failed: port is already allocated`

## Root Cause

The `ENV` Makefile variable was referenced in 6 targets (`docker-up`, `docker-down`, `docker-logs`, `docker-ps`, `docker-shell`, `docker-config`) via `$(if $(ENV),--env-file ../.env.$(ENV))` but was never given a default value. This meant:

- The `--warn-undefined-variables` flag (line 11) produced a warning for every target
- No `.env.*` file was loaded, so Docker Compose used unconfigured default port values
- If any default port was already occupied on the host (e.g., port 9005 by another process), the container failed to start

## Solution

Added `ENV ?= dev` in the Docker Compose Lifecycle section (line 182), just before `COMPOSE_FILE`. This:

- Provides a default value of `dev` for the `ENV` variable
- Eliminates the `undefined variable` warning
- Makes `make docker-up` automatically load `--env-file ../.env.dev` with proper port mappings
- Users can still override with `make docker-up ENV=test` or `ENV=staging`

## Prevention

- All Makefile variables referenced via `$(VAR)` should have a default value when `--warn-undefined-variables` is enabled
- Define defaults near the relevant section header using `?=` so they can be overridden from the command line
- When Docker Compose services use different port mappings per environment, always load the appropriate `.env.*` file
