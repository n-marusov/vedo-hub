# Package Manager Violation — npm install Broke pnpm node_modules During M2.5 Phase 2

**Date:** 2026-07-18 10:40 UTC
**Files:** package.json, node_modules/ (destroyed and rebuilt), tsconfig.json (briefly), vitest.config.ts (briefly)
**Severity:** medium

## Problem

During Phase 2 (Block A TDD) implementation of M2.5 GUI Wiring, the agent:

1. **Used `npm install --save-dev @types/node`** in a project that uses **pnpm** exclusively. This destroyed the pnpm symlink-based `node_modules` structure, poisoned `package.json` with `@types/node@^26.1.1` (wrong version for TS 5.5), and created a redundant `package-lock.json`.

2. **Compounded the error** by running `rm -rf node_modules && pnpm install --frozen-lockfile` (failed due to package.json drift), then `rm -rf node_modules && pnpm install --no-frozen-lockfile` (succeeded but left TypeScript language server cache stale).

3. **Attempted unnecessary fixes** for pre-existing IDE diagnostics (`vitest.config.ts` → `node:url` module resolution, `App.vue` → `lucide-vue-next` type declarations) using npm instead of pnpm, adding `/// <reference types="node" />` and `vitest.config.ts` to tsconfig `include` — all later reverted.

4. **Declared implementation complete** without running full-project diagnostics (`diagnostics` without file filter), missing 26 IDE errors and 2 warnings that were visible before the agent's npm intervention.

**Net result:** 40 minutes of cascade repair (revert tsconfig, revert vitest.config, restore package.json from git, `rm -rf node_modules`, `pnpm install`). The TypeScript language server cache remains stale after node_modules rebuild, requiring IDE restart.

## Root Cause

### Primary: Package manager abuse

The agent ran `npm install` without checking which package manager the project uses. The project uses pnpm (evidenced by `pnpm-lock.yaml` and pnpm-specific `node_modules/.pnpm/` symlink structure). Running `npm install` side-by-side with pnpm corrupts the node_modules:

- npm creates a flat `node_modules/` with real package copies
- pnpm uses a content-addressable store with symlinks
- Mixing them causes module resolution failures for both package managers

The correct command would have been `pnpm add -D @types/node`.

### Secondary: Skipped full-project diagnostic gate

The `$aif-implement` skill-context addendum requires a full-service static-analysis gate after implementation. The agent only ran `biome check` on explicitly changed files and `vitest` on SPARQLPage only. The full `diagnostics` tool call (without path filter) was never made before declaring the task complete.

### Tertiary: Fixing pre-existing issues within a scoped task

The `vitest.config.ts` `node:url` error and `App.vue` `lucide-vue-next` error were pre-existing and unrelated to Phase 2 Task 2.4. Attempting to fix them:
- Violated the scope of Task 2.4 (wire SPARQLPage, not fix tooling config)
- Triggered the npm install cascade
- Added unnecessary complexity to the verification

1. **Reverted all spurious changes:**
   - `package.json` — restored from git (`git checkout`)
   - `vitest.config.ts` — removed `/// <reference types="node" />`
   - `tsconfig.json` — removed `vitest.config.ts` from `include`

2. **Rebuilt node_modules correctly:**
   - `rm -rf node_modules package-lock.json`
   - `pnpm install` (successful, all 237 packages restored)

3. **Fixed legitimate Phase 2 bugs found during diagnostics:**
   - `VersioningPage.vue:153` — prefixed unused `compareResult` with `_`
   - `OntologyWorkspace.vue:786` — removed empty CSS ruleset `.ai-panel__section`

4. **Updated traceability matrix** (`.ai-factory/traceability/traceability.ttl`):
   - Added 3 vdo:TestSuite entries for M2.5 vitest specs
   - Added 4 vdo:CodeArtifact entries for M2.5 mock infrastructure and test utilities

## Prevention

### For agents working in this project:

1. **ALWAYS check for pnpm-lock.yaml before any install command.** If it exists, use `pnpm add`/`pnpm install` exclusively. Never run `npm install` in a pnpm project.

2. **Before declaring a task complete, run `diagnostics` tool call WITHOUT file path filter.** This shows the full IDE error/warning surface. If errors exist that were not present before the task, investigate before marking `[x]`.

3. **Respect task scope.** Pre-existing IDE diagnostics in files not touched by the task are NOT the agent's responsibility to fix. Flag them as `WARN [diagnostics]` in the verification report and move on.

4. **If `@types/node` or similar tooling types are needed for a config file, use the correct package manager:**
   ```
   pnpm add -D @types/node
   ```

5. **After any `rm -rf node_modules && pnpm install`:**
   - Verify modules resolve (`node -e "require.resolve('key-package')"`)
   - Run tests to confirm runtime resolution works
   - Restart TypeScript language server / IDE to clear stale module cache
   - The IDE may show transient errors until TS server restarts

### For the `$aif-verify` workflow refinement:

The `$aif-verify` skill should explicitly call `diagnostics` (no path filter) as an early gate, not rely on manual discovery of IDE errors. Pre-existing errors should be categorized and reported, not fixed within an implementation task.
