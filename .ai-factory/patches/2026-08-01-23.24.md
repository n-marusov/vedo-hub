# GUI localization: hardcoded English shell + no browser language detection

**Date:** 2026-08-01 23:24
**Files:** apps/services/frontend/src/App.vue, apps/services/frontend/src/composables/useI18n.ts, apps/services/frontend/src/main.ts, apps/services/frontend/src/locales/en.json, apps/services/frontend/src/locales/ru.json, apps/services/frontend/src/__tests__/useI18n.spec.ts
**Severity:** medium

## Problem

The app shell (sidebar navigation menu + header) rendered in English while
page content was in Russian. Also, the interface language was hardcoded to
Russian (`i18n.setLocale("ru")` in main.ts) and never followed the user's
browser language preferences.

Observed: menu showed "Home", "Groups", "Projects", "Merge requests", etc.
while the page body was fully Russian. Changing the browser language had no
effect on the interface.

## Root Cause

Two independent defects:

1. **Shell never used i18n.** `App.vue` (the active shell) hardcoded English
   strings: sidebar `mainItems` labels, header aria-labels, search placeholder,
   "Workspace" header, "Help", "Expand/Collapse sidebar", and the theme
   switch aria-label. The legacy `components/Header.vue` and
   `components/Sidebar.vue` had the same problem but were dead code (never
   imported). Only page components used `t()` from `useI18n`, so pages were
   translated while the shell was not.

2. **Locale resolution ignored browser preferences.** `useI18n.ts`
   `readPersistedLocale()` returned the hardcoded `DEFAULT_LOCALE = "ru"`
   whenever localStorage had no entry, and `main.ts` unconditionally called
   `setLocale("ru")`. `navigator.languages` / `navigator.language` were never
   consulted, so a user with an English browser still got Russian.

## Solution

1. `useI18n.ts`:
   - Added `detectBrowserLocale()` which scans `navigator.languages` (fallback
     `navigator.language`) and returns the primary language tag if it matches
     `ru` or `en`.
   - Added `resolveInitialLocale()` with priority:
     `localStorage` (explicit user choice) → browser preferences → `"ru"` default.
   - Exposed `initialLocale()` on the composable so `main.ts` reuses the same
     resolution order.

2. `main.ts`: replaced `i18n.setLocale("ru")` with
   `i18n.setLocale(i18n.initialLocale())`.

3. `App.vue`:
   - Imported `useI18n`; converted `mainItems` from a plain array to a
     `computed` whose labels come from `t("nav.*")` keys (added a `key` field
     to identify items).
   - Removed the old label-matching `watch` on `navCounts` — the computed
     reads `navCounts.*` directly, so badges update reactively on their own.
   - Replaced every hardcoded template string with `t()` calls; added
     `key`-based identification instead of English-label matching.
   - `themeLabel` computed now uses `t("theme.switch_to_light|dark")`.

4. Locale files: added matching keys to `ru.json` and `en.json`
   (`nav.workspace`, `nav.main_navigation`, `nav.expand_sidebar`,
   `nav.collapse_sidebar`, `header.*`, `theme.switch_to_*`). Verified both
   files have identical key sets (126 keys each).

## Prevention

- When adding UI text to shell/global components, ALWAYS route it through
  `t()` — never hardcode English strings. Reviewers should flag literal
  strings in `<template>` of shared components.
- The initial locale must resolve as:
  explicit user choice → browser preference → project default. Never force
  a locale in the app entry point.
- When the i18n module gains a new locale, the test suite should include a
  key-parity check between locale JSON files (missing keys fall back to
  English silently, which hides drift).
- Component tests that mount `App.vue` assert structure, not label text —
  keep it that way so localization changes don't break them.
