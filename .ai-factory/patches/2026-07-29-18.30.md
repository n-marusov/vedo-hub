# Integration tests must be spec-driven, not hand-written independently

**Date:** 2026-07-29 18:30
**Files:** .ai-factory/rules/base.md
**Severity:** medium

## Problem

Three integration tests in ontology-service (`individual_integration_test.rs`) failed because they were written without reference to the actual handler code:

- `test_create_individual_stores_in_neo4j` expected HTTP 200 OK, but the handler returns 201 CREATED
- `test_get_individual_returns_data`, `test_update_individual_changes_label`, and `test_delete_individual_removes_from_neo4j` used direct Neo4j `CREATE` queries that skipped the `INSTANCE_OF` relationship, causing the handler to return 404 Not Found

Additionally, `test_export_rdfxml_returns_content` used `format=rdfxml` instead of the correct `format=rdf-xml`, because the only valid formats (`turtle`, `rdf-xml`, `owl-xml`) were not checked against the handler before writing the test.

## Root Cause

The tests were written without reading the handler source code. Each assertion (status code, URL, format parameter) was guessed rather than derived from the implementation:

1. `create_individual_handler` returns `(StatusCode::CREATED, Json(...))` — 201 was verified in the handler but the test assumed 200
2. `IndividualRepository::create()` creates `INSTANCE_OF` edges, but the test's direct `CREATE (i:Individual ...)` did not — the handler requires that edge for GET/PUT/DELETE
3. The router matches `"rdf-xml"` (with hyphen) but the test used `"rdfxml"` (no hyphen)

## Solution

Added a new rule to `.ai-factory/rules/base.md` titled **Integration Tests Must Be Spec-Driven** that mandates:

- Status codes and response shapes must match the handler's actual return types
- Direct DB seeding must replicate all handler-created relationships
- API endpoints should be preferred for test setup over raw DB queries
- AI agents must read handler source code before generating test assertions

## Prevention

- When writing integration tests, always read the handler first before writing assertions
- When creating test data via DB queries, ensure all required relationships are present
- When using `$aif-plan` or `$aif-implement` to generate tests, include a step: "Read handler source and derive test expectations"
- Code review should catch mismatches between test expectations and handler signatures
