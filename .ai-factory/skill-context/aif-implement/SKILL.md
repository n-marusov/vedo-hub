## Completion Rule

A task may be marked `[x]` only when:

1. The base task-specific verification passes.
2. The additional full-service static-analysis checkpoint for selected ecosystems
   has no errors.
3. Any skipped tools are explicitly reported as `WARN [lint] <tool> not available — skipping`.

If the static-analysis checkpoint finds errors:

- Keep the task as in-progress or blocked (`[~]` / `[!]`) according to severity.
- Report the failing command and representative file:line diagnostics.
- Do not claim implementation is complete.

This rule prevents the agent from declaring success while IDE-visible static-analysis
errors remain in the affected ecosystem.

### Security Code — Security Tests

**Source**: `2026-07-18-18.23.md` — M2 AI Ontology Creation (X-Admin-Override, X-Ontology-Visibility bypasses)
**Rule**: When implementing security-sensitive features (auth bypass guards, RBAC, input sanitization, prompt injection defense, encryption), include negative tests (BOLA/BFLA pattern, real HTTP dispatch) that prove the protection works. Overrides the base "DON'T write tests" rule when the change is security-related. Tests must dispatch a real HTTP request, not use mock assertions.

### LLM Prompt Injection Defense — Implementation Checklist

**Source**: `2026-07-18-18.23.md` — M2 AI Ontology Creation (dead code, Unicode bypass, missing length limits, nil provider, gRPC auth)
**Rule**: When implementing LLM-related features that send user input to LLM providers:

1. SanitizeUserInput/SanitizeLLMInput/ValidateLLMOutput (or equivalent) must be called in ALL code paths — not merely defined
2. NFC normalization strips zero-width characters before pattern matching
3. MaxTextLength/MaxFeedbackLength limits must be enforced with PAYLOAD-TOO-LARGE error codes
4. All user-supplied values interpolated into prompts must be sanitized before reaching the LLM
5. Use http.NewRequestWithContext() for all outbound LLM calls with io.LimitReader (10MB limit)
6. Include nil provider guards before calling LLM provider methods
7. Ensure gRPC auth interceptor propagates JWT tokens for inter-service calls

### Query Parameterization Rule

**Source**: `2026-07-14-20.30.md` — M1 Review (SQL injection, Cypher injection, SPARQL→Cypher injection)
**Rule**: When implementing code that interacts with databases (Neo4j, PostgreSQL), always use parameterized queries — never string-interpolate user input. When calling external services, always check `.error_for_status()` and propagate transport errors — never return `Ok(())` on failure.

### Docker Workspace-Aware Builds

**Source**: `2026-07-17-22.00.md` — Docker Compose build fixes (Rust workspace, Go replace directives, lockfile sync)
**Rule**: When creating or modifying Dockerfiles for Rust workspace services, set build context to the workspace root, copy all member `Cargo.toml` files, and build with `-p <service>`. For Go services with `replace` directives, copy sibling modules to paths matching replace targets. After any `docker-compose.yml` change, run `docker compose config` to validate YAML. After `package.json` changes, run `pnpm install` (or equivalent) to sync lockfile.

### Phase Migration Checklist

**Source**: `2026-07-17-22.00.md` (ai-orchestration-service migration), `2026-07-16-18.30.md` (template handler migration)
**Rule**: When moving code between services (phase migration), cross-compile the destination service before considering migration complete. Verify imports resolve, all referenced functions exist in the destination package, and the destination builds with `go vet`/`cargo check`. When sharing code through `replace` directives, verify Docker build context includes the shared modules.

### OpenAPI Spec Update for New REST Endpoints

**Source**: `2026-07-19-19.20.md` (outdated OpenAPI spec during M3 milestone)
**Rule**: When implementing new REST endpoints, update the OpenAPI spec at `src/services/api-gateway/docs/openapi.json` in the same implementation task. Add path definitions, request/response schemas, error responses, and bump the version. Do not defer spec updates to a later task — they are part of the implementation.

### Rust — Update AppState Constructors When Adding Fields

**Source**: `2026-07-19-18.00.md` (missing `auth_client` field in ontology-service tests)
**Rule**: When adding a required field to a shared Rust struct (`AppState`, service config, etc.), run `cargo test --no-run` for the affected crate to detect all construction sites (production `::new()` calls and test initializers) that need updating. Rust's exhaustiveness check (`E0063`) catches these at compile time, but only if the full test suite is compiled.

### Go Integration Test Build Tag Convention

**Source**: `2026-07-19-21.29.md` (commenting-service integration tests)
**Rule**: All Go test files that depend on external infrastructure (PostgreSQL, Neo4j, network services) MUST have a `//go:build integration` constraint (both Go 1.17+ and legacy syntax). Use the `_integration_test.go` suffix consistently. Without this constraint, `go test ./...` will attempt to compile and run these tests unconditionally, causing pipeline failures when the external service is unavailable.

### Nginx Rewrites for New API Paths

**Source**: `2026-07-19-23.31.md` (nginx missing rewrite for /api/v1/health and /api/v1/ready)
**Rule**: When adding new API endpoints where the external path (`/api/v1/...`) differs from the internal handler path (`/health`, `/ready`, etc.), add a corresponding nginx rewrite rule in `src/services/frontend/nginx.conf` using an exact-match (`=`) location block and the `rewrite ... break` directive. Review the Vite dev server's `proxy` rewrite rules in `vite.config.ts` and ensure every rewrite has a production equivalent in `nginx.conf`.

### WCAG AA Color Choice for Dark Themes

**Source**: `2026-07-20-13.15.md` (muted-foreground #6b7280 on #101010 failed 4.5:1)
**Rule**: When implementing dark theme UI elements, verify all color choices against WCAG AA contrast thresholds (4.5:1 for normal text, 3:1 for large text). For muted/secondary text on dark card backgrounds (`--card: #101010`), prefer shades of gray that pass the 4.5:1 threshold. The existing `--muted-foreground: #8a94a6` is a known-safe value for this project. Use axe-core's `color-contrast` rule or an online contrast checker before finalizing color tokens.
