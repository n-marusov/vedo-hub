== Overview

This runbook describes the operational procedure for rolling back a major-version migration in VEDO Core. It covers fast rollback (within 60 minutes), late rollback (after 60 minutes), partial commit rollback, and sandbox environment recreation.

== Prerequisites

* Authenticated operator with platform/admin role
* Pre-migration backup ID and verified integrity checksum
* Cluster access (kubectl, SSH, or management API)
* Monitoring dashboard for migration observability

== Fast Rollback (0–60 Minutes Post-Upgrade)

=== Step 1: Verify Rollback Eligibility

[source,bash]
----
# Check elapsed time since upgrade
curl -s /api/v1/migrations/{migrationId}/status | jq '.elapsedMinutes'
# Must be <= 60 for fast rollback
----

=== Step 2: Stop Services

Stop all application services or place them in read-only mode to prevent data divergence.

[source,bash]
----
# Example: scale down deployment
kubectl scale deployment vedo-api --replicas=0
kubectl scale deployment vedo-worker --replicas=0
----

=== Step 3: Restore Pre-Migration Backup

Restore the database and storage volumes from the verified pre-migration backup.

[source,bash]
----
# Example: restore from backup artifact
backupctl restore --backup-id={preMigrationBackupId} \
  --target=vedo-db \
  --verify-checksum=true
----

=== Step 4: Run Integrity Checks

Verify ontology consistency, version-store integrity, and data completeness before reopening traffic.

[source,bash]
----
# Example: trigger integrity verification
curl -X POST /api/v1/migrations/{migrationId}/integrity-check
# Wait for status: passed
----

=== Step 5: Restore Traffic

[source,bash]
----
kubectl scale deployment vedo-api --replicas=3
kubectl scale deployment vedo-worker --replicas=2
----

Expected RTO: 30–60 minutes.
Expected data loss: elapsed minutes since upgrade.

== Late Rollback (60+ Minutes Post-Upgrade)

=== Assessment

After 60 minutes, direct rollback is discouraged because users may have created new data. Evaluate the following options:

1. *Hotfix*: Deploy a forward fix on the current version (preferred).
2. *Hotfix with data migration*: If schema changes are incompatible, write a data migration script.
3. *Escalated rollback*: Requires platform-admin approval and explicit data-loss communication to affected users.

=== Procedure

[source,bash]
----
# Request escalation
curl -X POST /api/v1/migrations/{migrationId}/escalate \
  -d '{"reason": "late rollback with user data"}' \
  -H "Authorization: Bearer {token}"
----

Wait for approval before proceeding with any data-affecting operation.

== Partial Commit Rollback

When only specific VEDO commits need reversal, use the commit-level partial rollback mechanism instead of a full database downgrade.

[source,bash]
----
# Roll back individual commits
vedoctl commit rollback --commit-id={commitId}
----

This does not affect the database schema or other tenants' data.

== Sandbox Rollback

Sandbox environments may be recreated from scratch rather than restored from backup. Use the infrastructure-as-code provisioning scripts.

[source,bash]
----
# Recreate sandbox environment
terraform destroy -target=sandbox && terraform apply -target=sandbox
----

== Rollback Decision Matrix

|===
| Elapsed Time | Rollback Type | Action | Approval Required | RTO

| 0–60 min | fast | restore_pre_migration_backup | platform-oncall | 30–60 min
| 60+ min | late | apply_hotfix or escalate | platform-admin | 120+ min
| N/A | partial | partial_commit_rollback | platform-oncall | 30 min
| N/A | sandbox | recreate_environment | platform-oncall | 90 min
|===

== Data Loss Communication

If users created new data between upgrade and rollback, the following must occur before proceeding:

1. Identify affected users and their data scope.
2. Notify users via the communication channel with expected data loss window.
3. Obtain explicit acknowledgment or proceed at the direction of platform-admin.

== Rollback Prevention Checklist

Before starting any rollback, confirm the following:

* [ ] Pre-migration backup exists and checksum is verified
* [ ] Operator has authenticated session with platform/admin role
* [ ] Rollback window has not expired for fast rollback
* [ ] Data-loss communication plan is ready (for late rollback)
* [ ] Monitoring and alerting are active for the rollback duration
* [ ] Audit logging is enabled for all rollback operations

== Security Notes

* Rollback runbooks must not print secrets or backup credentials.
* Restore operations require privileged operator authorization and audit logging.
* Backup artifacts used for rollback must be integrity-checked before restore.
* All rollback decisions and approvals must be recorded in the audit log.

== Observability Events

The following structured events are emitted during rollback:

* `rollback.start` — Rollback initiated with migration ID and rollback type
* `rollback.checkpoint` — Intermediate step completed (e.g., services stopped)
* `rollback.integrity` — Integrity check result (passed/failed)
* `rollback.approval` — Escalation approval or denial
* `rollback.restore` — Backup restore completed
* `rollback.traffic` — Traffic restoration complete
* `rollback.complete` — Rollback finished with final RTO and data loss metrics

Alerts are triggered at P0 for any rollback operation exceeding the expected RTO.
