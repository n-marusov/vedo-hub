== Протокол Incident Commander

При возникновении инцидента назначаются роли:

|===
| Роль | Ответственный | Задачи

| xref:glossary.adoc#incidentCommander[Incident Commander] (IC)
| Наиболее опытный дежурный
| Координация, коммуникация, принятие решений

| Communications Lead
| Представитель поддержки
| Уведомление клиентов, статус-апдейты

| Operations Lead
| SRE / DevOps
| Техническое восстановление сервиса
|===

=== Процесс

. **Обнаружение** — алерт или сообщение пользователя
. **Определение severity** — P0, P1, P2, P3
. **Назначение IC** — первый ответивший берёт на себя роль
. **Диагностика** — определение причины
. **Восстановление** — применение fix'а
. **Коммуникация** — обновление статуса
. **Post-mortem** — анализ причин и предотвращение

== P0: Сервис недоступен (Service Unavailable)

=== Признаки

* HTTP 503 на всех endpoints
* Все сервисы не отвечают на health checks
* Полная потеря connectivity

=== Диагностика

[source,bash]
----
# 1. Проверка кластера K8s
kubectl get pods --all-namespaces
kubectl describe node

# 2. Проверка health API Gateway
curl -f https://vedo.example.com/health

# 3. Комплексная диагностика
vedo-cli diagnose

# 4. Проверка трассировки
vedo-cli diagnose trace --id $(kubectl logs \
  -n vedo-system deployment/api-gateway \
  --tail=1 | grep -oP 'trace_id=\K[a-f0-9]+')
----

=== Восстановление

. **Проверить Ingress/Network**: статус load balancer, DNS, TLS сертификаты
. **Проверить ресурсы узлов**: `kubectl top nodes` — возможен OOM или CPU starvation
. **Перезапустить критичные поды**:
+
[source,bash]
----
kubectl rollout restart deployment/api-gateway -n vedo-system
kubectl rollout restart deployment/ontology-service -n vedo-system
kubectl rollout restart deployment/versioning-service -n vedo-system
----
. **Проверить БД**: статус Neo4j и PostgreSQL
+
[source,bash]
----
kubectl exec -it statefulset/neo4j -n vedo-system -- neo4j status
kubectl exec -it statefulset/postgresql -n vedo-system -- pg_isready
----
. **Если не помогло — fast rollback последнего изменения**:
+
[source,bash]
----
vedo-cli migrate rollback --backup-id last-good-backup
----
. **В крайнем случае — восстановление из backup**

[WARNING]
====
При P0 инциденте восстановление сервиса имеет приоритет над расследованием причины. После восстановления проводится post-mortem.
====

== P1: Деградация производительности

=== Признаки

* p95 latency > 1 сек
* Частичная недоступность функционала
* Ошибки rate limiting у клиентов

=== Диагностика

[source,bash]
----
# 1. Проверка метрик сервисов
vedo-cli diagnose

# 2. Анализ latency Grafana
# RED-дашборд: проверка Rate, Errors, Duration

# 3. Проверка медленных запросов Neo4j
kubectl exec -it statefulset/neo4j -n vedo-system -- \
  cypher-shell "CALL dbms.listQueries()"

# 4. Проверка активных соединений PostgreSQL
kubectl exec -it statefulset/postgresql -n vedo-system -- \
  psql -c "SELECT * FROM pg_stat_activity WHERE state = 'active';"
----

=== Восстановление

. **Redis cache**: проверить hit ratio, при необходимости разогреть кэш
+
[source,bash]
----
vedo-cli cache warmup
----
. **Neo4j**: проверить медленные запросы, добавить индексы при необходимости
. **PostgreSQL**: проверить autovacuum, активность WAL
. **Горизонтальное масштабирование**:
+
[source,bash]
----
kubectl scale deployment/ontology-service --replicas=5 -n vedo-system
----
. **Circuit Breaker**: если сервис перегружен, circuit breaker может временно блокировать запросы — дождаться восстановления

== Диагностика по trace_id

=== Стандартный Flow

[source,bash]
----
# 1. Получить trace_id из ошибки пользователя или лога
# 2. Выполнить диагностику
vedo-cli diagnose trace --id abc123def456

# Результат:
# ✅ Trace found in Tempo
# 📊 Span: ontology-service / 245ms (p95: 120ms)
# 📊 Span: neo4j / 200ms
# 📊 Span: auth-service / 30ms
# 📝 Logs from Loki:
#    ontology-service: "SLOW_QUERY: MATCH (n:Class)..." at 14:30:00
# 📈 Metrics from Prometheus:
#    neo4j_query_duration_seconds: 0.200 (p95: 0.150)
----

=== Поиск trace по сервису

[source,bash]
----
# Поиск всех trace с ошибками в сервисе за последний час
{service="ontology-service"} |= "ERROR"
----

=== Анализ медленных trace

[source,bash]
----
# Top 10 медленных запросов за последние 15 минут
sort_desc(avg(otel_span_duration_seconds)) by (service, span_name)
----

== Emergency Read-Only Mode

=== Активация

[source,bash]
----
vedo-cli emergency readonly

# Система переведена в режим «только чтение» (max 60s)
----

[CAUTION]
====
Режим readonly останавливает все мутирующие операции. Используйте для предотвращения повреждения данных при сбое.
====

=== Снятие режима

[source,bash]
----
vedo-cli emergency clear

# Система возвращена к нормальной работе
----

== Восстановление после отказа

=== Полный сбой кластера

.Procedure

. Развернуть новый кластер Kubernetes
. Установить VEDO Core через Helm (без данных)
. Выполнить восстановление из последнего валидного backup:
+
[source,bash]
----
vedo-cli restore --id bkp-latest-verified
----
. Проверить целостность
. Возобновить трафик

=== Сбой одной БД (Neo4j / PostgreSQL)

[source,bash]
----
# Neo4j: проверка кластера
kubectl exec -it statefulset/neo4j -n vedo-system -- \
  cypher-shell "CALL dbms.cluster.overview()"

# Neo4j: переизбрание primary
kubectl exec -it statefulset/neo4j-1 -n vedo-system -- \
  neo4j-admin cluster designate --role CORE

# PostgreSQL: promotion standby to primary
kubectl exec -it statefulset/postgresql-1 -n vedo-system -- \
  pg_ctl promote
----

=== Сбой Redis кластера

[source,bash]
----
# Проверка кластера
redis-cli -h redis-service -p 6379 cluster info

# Перезапуск кластера (потеря кэша, данные не критичны)
kubectl rollout restart statefulset/redis -n vedo-system

# Разогрев кэша после восстановления
vedo-cli cache warmup
----

=== Сбой RabbitMQ

[source,bash]
----
# Проверка очередей
kubectl exec -it statefulset/rabbitmq -n vedo-system -- \
  rabbitmqctl list_queues

# Восстановление: перезапуск
kubectl rollout restart statefulset/rabbitmq -n vedo-system
----

== Восстановление базы данных

=== Neo4j Recovery

[source,bash]
----
# Проверка состояния БД
neo4j-admin check --database=neo4j

# Восстановление из backup
neo4j-admin restore \
  --from=/backup/neo4j-20260520.dump \
  --database=neo4j

# Запуск после восстановления
neo4j start
----

=== PostgreSQL Recovery

[source,bash]
----
# PITR восстановление
pg_restore -Fc -d vedo /backup/postgres-20260520.dump

# Восстановление WAL
pg_ctl start -D /var/lib/postgresql/data \
  -o "-c recovery_target_time='2026-05-20 14:30:00'"
----

[NOTE]
====
Все процедуры восстановления БД документированы в xref:backup-policy.adoc[Политике резервного копирования]. Целевой RTO: 4 часа (standard), 60 минут (fast rollback).
====

== Merge Conflict Resolution (Server Side)

=== Обнаружение конфликта

[source,bash]
----
vedo-cli mr list --status conflict
----

=== Разрешение конфликта

.Procedure

. Получить детали конфликта:
+
[source,bash]
----
vedo-cli mr get --id mr-42 --show-conflicts
----
. Автоматическое разрешение (3-way merge):
+
[source,bash]
----
vedo-cli mr merge --id mr-42 --auto-resolve
----
. Если автоматическое разрешение невозможно — ручное через web UI:
   * Открыть MR в веб-интерфейсе
   * Выбрать разрешение для каждого конфликта
   * Подтвердить слияние
. После разрешения — выполнить merge:
+
[source,bash]
----
vedo-cli mr merge --id mr-42
----
