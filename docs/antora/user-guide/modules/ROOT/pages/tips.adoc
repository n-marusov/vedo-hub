= Советы и рекомендации
:description: Практические советы для эффективной работы с онтологиями в VEDO Core.
:sectnums:
:toc: left

== Моделирование онтологии

=== Начинайте с малого

Не пытайтесь создать полную онтологию за один раз. Начните с 5-10 ключевых xref:glossary.adoc#class[классов] и постепенно расширяйте модель.

Рекомендуемый порядок:

. Определите основные классы предметной области.
. Добавьте xref:glossary.adoc#property[свойства] между классами.
. Уточните xref:glossary.adoc#taxonomy[иерархию] (родительские/дочерние классы).
. Настройте характеристики свойств (транзитивность, симметричность).
. Наполните xref:glossary.adoc#individual[индивидами] для тестирования.

=== Используйте осмысленные имена

Давайте классам и свойствам понятные имена на русском языке (транслитерация для URI). Плохо: `c1`, `prop42`. Хорошо: `Организация`, `работаетВ`, `идентификаторИНН`.

=== Пишите описания (rdfs:comment)

Каждый класс и свойство должны иметь описание на русском языке. Это критически важно для понимания модели другими участниками команды и для xref:glossary.adoc#introspection[Introspection] в визуальном конструкторе SPARQL.

=== Используйте множественное наследование осмысленно

xref:glossary.adoc#facetedClassification[Фасетная классификация] — мощный инструмент, но избыточное множественное наследование усложняет модель. Придерживайтесь принципа: класс имеет несколько родителей только если он действительно является подтипом каждого из них.

== Управление версиями

=== Коммитьте часто

Делайте xref:glossary.adoc#ontologyCommit[коммиты] после каждого логически завершённого изменения. Это упрощает откат и рецензирование.

=== Пишите осмысленные сообщения коммитов

Формат сообщения:

[source]
----
Краткое описание (до 50 символов)

Подробное описание: что изменено, зачем, на что влияет.
----

=== Работайте в ветках

Никогда не редактируйте `main` напрямую. Создавайте xref:glossary.adoc#ontologyBranch[ветки] для каждой задачи:

* `feature/add-new-module` — новая функциональность
* `fix/incorrect-hierarchy` — исправление ошибок
* `refactor/rename-classes` — рефакторинг

=== Делайте Merge Request даже для небольших изменений

Привычка создавать xref:glossary.adoc#mergeRequest[Merge Request] для любых изменений в `main` обеспечивает:

* Контроль качества (ревью)
* Прозрачность изменений
* Сохранение контекста для будущих поколений

== SPARQL

=== Начинайте с визуального конструктора

Если вы не знакомы с синтаксисом xref:glossary.adoc#sparql[SPARQL], используйте визуальный конструктор — он генерирует корректные запросы на основе xref:glossary.adoc#introspection[Introspection] схемы.

=== Всегда указывайте LIMIT

Это защищает как сервер, так и вас от непреднамеренно тяжёлых запросов. Даже если вы ожидаете мало результатов, укажите лимит.

=== Используйте префиксы

В текстовом редакторе SPARQL определите префиксы для часто используемых пространств имён:

[source,sparql]
----
PREFIX ex: <http://example.org/my-ontology#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
----

== Коллаборация

=== Комментируйте решения

Оставляйте xref:tasks.adoc#merge-requests[комментарии] к классам и свойствам, объясняя, почему принято то или иное решение. Это создаёт корпоративную память.

=== Используйте @упоминания

Для привлечения внимания коллеги используйте `@username` в комментарии. Пользователь получит уведомление.

=== Проводите регулярные ревью

Выделите время для рецензирования Merge Request коллег. Свежий взгляд часто находит ошибки, которые автор не замечает.

== Производительность

=== Используйте дерево вместо графа

Для навигации по большим онтологиям предпочитайте дерево классов — оно работает быстрее графа. Граф используйте для анализа связей.

=== Фильтруйте граф

При работе с графом ограничивайте глубину отображения (2-3 уровня) и используйте фильтры по типу узлов.

=== Групповые операции

Для массовых изменений индивидов используйте групповое редактирование (F4.8) вместо поодиночного редактирования каждого экземпляра.

== Импорт/Экспорт

=== Используйте Turtle для интеграции

Для обмена данными с другими системами и для интеграции с Git используйте xref:glossary.adoc#turtle[Turtle] — каноническая сериализация обеспечивает стабильный diff.

=== Проверяйте импорт на тестовой онтологии

Перед импортом в продуктивную онтологию протестируйте операцию на копии. Используйте стратегию *New Version* при неопределённости.
