== Общие принципы

* **Читаемость:** код пишется для людей, а не для машин
* **Идиоматичность:** следуйте соглашениям языка, используйте стандартные паттерны
* **Тестируемость:** код должен легко покрываться тестами
* **Безопасность:** никаких секретов в коде, предварительно подготовленные запросы для SPARQL
* **Производительность:** zero-cost abstractions, минимизация аллокаций в горячем пути

== Rust

=== Стиль

* Форматирование: `rustfmt` (стандартный)
* Линтер: `clippy` с `-W clippy::pedantic -W clippy::nursery`
* Максимальная длина строки: 120 символов
* Именование: `snake_case` для функций/переменных, `CamelCase` для типов, `SCREAMING_SNAKE_CASE` для констант

=== Запрещено

* `unwrap()`, `expect()` в production-коде — используйте `anyhow::Context` или кастомные ошибки
* `unsafe` без xref:adr.adoc[ADR] и комментария `// SAFETY:`
* Глобальные `static mut`
* Panic в библиотечном коде

=== Рекомендации

[source,rust]
----
// Правильно: обработка ошибок через anyhow
use anyhow::{Context, Result};

pub fn create_class(name: &str) -> Result<Class> {
    let validated = validate_name(name)
        .context("Invalid class name")?;
    // ...
}

// Правильно: идиоматичная работа с Option
let value = opt
    .map(|x| x * 2)
    .unwrap_or(0);

// Правильно: типы-обёртки для domain
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct OntologyId(Uuid);
----

=== Тестирование

* Юнит-тесты: в каждом файле через `#[cfg(test)] mod tests`
* Интеграционные: в `tests/`
* Property-based: `proptest` или `quickcheck`

[source,rust]
----
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_create_class_success() {
        let result = create_class("PneumaticCylinder");
        assert!(result.is_ok());
    }

    #[test]
    fn test_create_class_invalid_name() {
        let result = create_class("");
        assert!(result.is_err());
    }
}
----

== Go

=== Стиль

* Форматирование: `gofmt` (стандартный)
* Линтер: `golangci-lint` с включёнными `errcheck`, `govet`, `staticcheck`
* Именование: `camelCase` для неэкспортируемого, `CamelCase` для экспортируемого
* Максимальная длина строки: 120 символов

=== Запрещено

* `panic()` в production-коде
* `log.Fatal()` в библиотечном коде
* Пустые `interface{}` без необходимости — используйте `any`
* `init()` функции без ADR

=== Рекомендации

[source,go]
----
// Правильно: обработка ошибок
func CreateClass(ctx context.Context, name string) (*Class, error) {
    if err := validateName(name); err != nil {
        return nil, fmt.Errorf("validate class name: %w", err)
    }
    // ...

// Правильно: интерфейсы — маленькие
type NodeReader interface {
    GetNode(ctx context.Context, id OntologyID) (*Node, error)
    ListChildren(ctx context.Context, id OntologyID) ([]*Node, error)
}

// Правильно: контекст — первый параметр
func (s *Service) CreateNode(ctx context.Context, req *CreateRequest) (*Node, error) {
    // ...
}
----

== Python

=== Стиль

* Форматирование: `ruff format`
* Линтер: `ruff check` с правилами `E`, `F`, `I`, `N`, `W`
* Типизация: обязательна, `mypy --strict`
* Именование: `snake_case` для функций/переменных, `CamelCase` для классов, `SCREAMING_SNAKE_CASE` для констант

=== Запрещено

* `except: pass`
* Глобальные мутируемые переменные
* Циклические импорты — используйте TYPE_CHECKING для аннотаций

=== Рекомендации

[source,python]
----
from typing import Self
from pydantic import BaseModel

# Правильно: типизированная модель
class Node(BaseModel):
    id: str
    label: str
    comment: str | None = None

# Правильно: асинхронный сервис
class OntologyService:
    async def create_class(self, name: str) -> Node:
        if not self._validate_name(name):
            raise ValueError(f"Invalid name: {name}")
        return await self._repo.save(Node(id=name, label=name))
----

== TypeScript / Vue 3

=== Стиль

* Форматирование: `prettier` с `--single-quote --trailing-comma all`
* Линтер: `eslint` с `@typescript-eslint/strict`
* Именование: `camelCase` для переменных/функций, `PascalCase` для компонентов/типов, `SCREAMING_SNAKE_CASE` для констант
* Типизация: строгая (`strict: true` в tsconfig)

=== Composition API

[source,typescript]
----
<script setup lang="ts">
import { ref, computed, onMounted } from 'vue'
import { useQuery } from '@vue/apollo-composable'
import gql from 'graphql-tag'

interface ClassNode {
  id: string
  label: string
  children?: ClassNode[]
}

const props = defineProps<{
  classId: string
}>()

const emit = defineEmits<{
  select: [id: string]
}>()

const { result, loading, error } = useQuery(gql`
  query GetClass($id: ID!) {
    node(id: $id) {
      id
      label
      children { id label }
    }
  }
`, { id: props.classId })

const selected = ref<string | null>(null)

function onSelect(id: string) {
  selected.value = id
  emit('select', id)
}
</script>
----

=== Запрещено

* `any` — используйте `unknown` и type guards
* Мутирующие props — используйте `emit`
* `console.log` в production-коде

== Формат коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/):

[source]
----
<type>(<scope>): <description>

[optional body]

[optional footer]
----

Типы:

|===
| Тип | Назначение
| `feat` | Новая функциональность
| `fix` | Исправление ошибки
| `refactor` | Рефакторинг без изменения поведения
| `test` | Добавление тестов
| `docs` | Изменения в документации
| `chore` | Обслуживание (зависимости, CI)
| `perf` | Оптимизация производительности
| `style` | Форматирование, lint
|===

Примеры:

[source]
----
feat(ontology): add SPARQL introspection endpoint
fix(versioning): handle empty delta in commit
refactor(api): extract validation middleware
test(ontology): add property-based tests for class hierarchy
docs(architecture): add C4 container diagram
----

== Code Review

=== Проверяющий проверяет

* Соответствует ли код xref:adr.adoc[ADR] и контрактам?
* Есть ли тесты для новой функциональности?
* Обработаны ли error cases?
* Нет ли утечки секретов/токенов?
* Соответствует ли код стандартам языка?
* Нет ли необработанных `unwrap()`/`panic()`/`except: pass`?

=== Автор

* MR не должен превышать 400 строк (если иное не согласовано)
* Каждый MR ссылается на issue или контракт
* Перед отправкой: `hlv check` должен проходить
* Все комментарии ревьюера должны быть разрешены до мержа

=== Процесс

1. Создайте ветку от `main`: `git checkout -b feature/my-feature`
2. Внесите изменения и закоммитьте
3. Запустите `hlv check` и локальные тесты
4. Создайте Pull Request / Merge Request
5. Получите как минимум одно одобрение
6. После одобрения — squash merge в `main`
