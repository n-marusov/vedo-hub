== Как участвовать

VEDO Core — проект с открытым исходным кодом. Мы приветствуем вклад сообщества: от исправления опечаток до реализации новых функций.

=== Для начала

1. Прочитайте xref:hlv.adoc[HLV-методологию] — это основа нашего процесса разработки
2. Ознакомьтесь с xref:coding.adoc[стандартами кодирования]
3. Настройте xref:devsetup.adoc[окружение разработчика]

== Процесс внесения изменений

```mermaid
sequenceDiagram
    actor Contributor as Контрибьютор
    participant Repo as Репозиторий
    actor Reviewer as Ревьюер

    Contributor->>Repo: Форк репозитория
    Contributor->>Repo: Создание ветки
    Contributor->>Contributor: Внесение изменений
    Contributor->>Contributor: Линтер + тесты
    Contributor->>Repo: Push + Pull Request
    Repo->>Reviewer: Уведомление
    Reviewer->>Repo: Ревью
    alt Одобрено
        Reviewer->>Repo: Merge
    else Замечания
        Reviewer->>Contributor: Комментарии
        Contributor->>Contributor: Исправления
        Contributor->>Repo: Обновление PR
    end
```

=== Пошаговая инструкция

1. **Форкните** репозиторий на GitHub
2. **Клонируйте** свой форк:
   ```
   git clone https://github.com/your-username/vedo-core.git
   cd vedo-core
   ```
3. **Добавьте upstream:**
   ```
   git remote add upstream https://github.com/vedo/vedo-core.git
   ```
4. **Создайте ветку:**
   ```
   git checkout -b feature/your-feature-name
   ```
5. **Внесите изменения**, следуя xref:coding.adoc[стандартам кодирования]
6. **Запустите тесты** и убедитесь, что всё проходит
7. **Создайте Pull Request** через GitHub

== Pull Request Checklist

Перед отправкой PR убедитесь:

* [ ] Код соответствует xref:coding.adoc[стандартам кодирования]
* [ ] Добавлены тесты для новой функциональности
* [ ] Все существующие тесты проходят
* [ ] `hlv check` проходит без ошибок
* [ ] Линтеры не выдают ошибок
* [ ] Документация обновлена (если применимо)
* [ ] Ветка основана на актуальном `main`
* [ ] Commit messages следуют [Conventional Commits](https://www.conventionalcommits.org/)
* [ ] PR не превышает 400 строк изменений
* [ ] Добавлены `@hlv` маркеры в тесты

== Pre-commit hooks (секреты)

Перед первым коммитом установите pre-commit хуки:

```bash
pip install pre-commit
pre-commit install
```

Хук запускает `gitleaks` (v8.18+) для проверки коммитов на наличие секретов.

- Если найден **Block-секрет** (production ключи) — коммит будет отклонён.
- Если найден **Warning** (тестовые ключи) — вы увидите предупреждение, но коммит пройдёт.

CI также проверяет секреты через `gitleaks` и GitLab Secret Detection, но pre-commit хук помогает избежать лишних итераций.

**Обход pre-commit** (только для экстренных случаев, с approval Security Lead):

```bash
git commit --no-verify -m "hotfix: ..."
```

Подробнее о порогах и типах секретов: `REQ-SEC-80` в `human/artifacts/requirements/REQ-NFR.SECURITY.security-requirements.md`.

== Adding Dependencies (License Compliance)

Перед добавлением новой зависимости убедитесь, что её лицензия допустима.

=== Проверка лицензии

1. Найдите лицензию библиотеки (README, Cargo.toml, package.json, go.mod).
2. Сверьте с таблицей допустимых лицензий:

| Разрешено | Запрещено | Требует проверки |
|-----------|-----------|------------------|
| MIT, Apache-2.0, BSD, ISC, MPL-2.0 | GPL, AGPL, LGPL, SSPL, CC-BY-NC | CDDL, EPL, JSON, WTFPL |

3. Если лицензия запрещена — **ищите альтернативу**.
4. Если лицензия требует проверки — **создайте issue** для Security Lead.

=== Локальная проверка

Перед коммитом можно запустить проверку лицензий локально:

```bash
# Rust
cargo deny check licenses

# Go
go-licenses check ./...

# Python
pip-licenses --allow-only "MIT;Apache-2.0;BSD;ISC"

# Node.js
npx license-checker --summary
```

=== Исключения

Если библиотека с запрещённой лицензией критически необходима:

1. Создайте issue с обоснованием.
2. Security Lead и Legal проведут оценку.
3. При одобрении — добавьте исключение в `licenses-exceptions.yaml`.
4. Исключение имеет срок действия (обычно 1 год).

**Без явного исключения CI упадёт, и PR не будет принят.**

Подробнее о лицензионной политике: `REQ-SEC-100` в `human/artifacts/requirements/REQ-NFR.SECURITY.security-requirements.md`.

== Вопросы безопасности

Если вы нашли уязвимость:

* **Не создавайте публичный issue**
* Напишите на `security@vedo.dev`
* Используйте наш [ключ PGP](https://vedo.dev/security/pgp-key.asc)

Мы отвечаем на отчёты об уязвимостях в течение 48 часов.

== Code of Conduct

Мы ожидаем от всех участников проекта уважительного и профессионального поведения.

* Будьте вежливы и конструктивны в обсуждениях
* Критикуйте код, а не человека
* Уважайте чужое время — отвечайте на ревью в течение 48 часов
* Принимайте решения на основе данных и контрактов, а не личных предпочтений

== Релизный процесс

Версионирование: [SemVer](https://semver.org/) (MAJOR.MINOR.PATCH).

1. Создание release branch `release/v1.x.x`
2. Заморозка новых функций
3. QA-цикл: тестирование, исправление багов
4. `/validate` — все mandatory gates
5. Создание тега `v1.x.x`
6. CI/CD: деплой в production
7. Публикация release notes
