== О ADR

Записи архитектурных решений (ADR) документируют ключевые технологические и архитектурные выборы, их контекст, рассмотренные альтернативы и последствия.

=== Формат ID

`ADR-<LEVEL>.<AREA>.<semantic-tag>`

* **LEVEL**: `BIZ` (бизнес) | `DES` (дизайн) | `IMPL` (реализация)
* **AREA**: `API` | `DATA` | `INFRA` | `SECURITY` | `UI` | `PROCESS` | `INTEGRATION` | `STACK`
* **semantic-tag**: короткая kebab-case метка (2–5 слов)

=== Структура ADR

Каждый ADR содержит:

* **Статус:** Черновик | Предложено | Принято | Устарело | Заменено
* **Дата:** ГГГГ-ММ-ДД
* **Контекст:** описание проблемы
* **Требование-источник:** ссылки на артефакты
* **Решение:** описание выбора
* **Рассмотренные альтернативы:** перечисление вариантов
* **Последствия:** положительные и отрицательные

== INFRA — Инфраструктура

=== ADR-DES.INFRA.monolith-vs-microservices
*Статус:* Принято

*Контекст:* Выбор архитектурного стиля для VEDO Core. Требуется поддержка 1 млн аксиом, параллельная работа, независимое масштабирование компонентов.

*Решение:* Микросервисная архитектура с разделением по доменным границам.

*Рассмотренные альтернативы:*
- **Монолит** — проще в разработке, но не позволяет независимо масштабировать Ontology Service и Versioning Service
- **Модульный монолит** — компромисс, но ограничивает изоляцию сбоев

*Последствия:*
- ✅ Независимое масштабирование и деплой сервисов
- ✅ Изоляция сбоев (сбой Metrics Service не влияет на Ontology Service)
- ✅ Возможность использовать разные языки (Rust, Go, Python)
- ❌ Сложность отладки распределённых запросов
- ❌ Дополнительные накладные расходы на сетевые вызовы

=== ADR-DES.INFRA.otel-observability-strategy
*Статус:* Принято

*Контекст:* Необходимость единого стандарта observability для распределённой системы.

*Решение:* Использовать OpenTelemetry как vendor-neutral стандарт сбора трейсов, метрик и логов, с экспортом в Grafana Stack (Prometheus, Loki, Tempo).

*Последствия:*
- ✅ Единый стандарт для observability
- ✅ Бесперебойное отслеживание производительности
- ❌ Дополнительная инфраструктура (Tempo, Loki, Prometheus)

=== ADR-DES.INFRA.vedo-cli-diagnostics-entrypoint
*Статус:* Принято

*Контекст:* Необходимость быстрой локализации инцидентов без доступа к Grafana.

*Решение:* Реализовать `vedo-cli diagnose --trace-id` как единую точку диагностики.

=== ADR-DES.INFRA.vedo-cli-admin-boundary
*Статус:* Принято

*Контекст:* Разграничение административных и пользовательских операций.

*Решение:* `vedo-cli` является единственной утилитой для операций, требующих повышенных привилегий (backup, restore, миграции, air-gap).

=== ADR-DES.INFRA.critical-alerts-strategy
*Статус:* Принято

*Контекст:* Предотвращение alert fatigue и гарантия реакции на критические события.

*Решение:* Внедрить иерархию алертов P0–P3 с обязательной эскалацией P0 через PagerDuty/Opsgenie.

=== ADR-DES.INFRA.telemetry-retention-strategy
*Статус:* Принято

*Контекст:* Баланс между стоимостью хранения и потребностями диагностики.

*Решение:* Метрики — 30 дней, логи — 30 дней, трейсы — 7 дней. Для Enterprise возможны индивидуальные настройки.

=== ADR-DES.INFRA.data-residency-region-strategy
*Статус:* Принято

*Контекст:* Требования 152-ФЗ и GDPR к хранению данных.

*Решение:* Поддержка региональной изоляции данных через привязку точек доступа к конкретному региону/кластеру.

=== ADR-DES.INFRA.airgap-offline-deployment-strategy
*Статус:* Принято

*Контекст:* Развёртывание в изолированных сетях (оборонная, нефтегазовая отрасли).

*Решение:* `vedo-cli` может генерировать полный offline-пакет с образами, Helm-чартами и документацией.

=== ADR-DES.INFRA.recovery-objectives-mandate
*Статус:* Принято

*Контекст:* Определение целевых показателей восстановления.

*Решение:* RTO ≤ 1 час, RPO ≤ 15 минут для Production. Для Enterprise возможно снижение RPO до 5 минут.

=== ADR-DES.INFRA.backup-policy-strategy
*Статус:* Принято

*Контекст:* Стратегия резервного копирования.

*Решение:* 3-2-1 стратегия: 3 копии, 2 носителя, 1 вне площадки. Неизменяемые копии (WORM) для защиты от ransomware.

=== ADR-DES.INFRA.ontology-publishing
*Статус:* Принято

*Контекст:* Публикация снапшотов онтологий для внешних пользователей.

*Решение:* Выделенный экземпляр Neo4j для опубликованных онтологий, изолированный от основного.

=== ADR-DES.INFRA.immutable-backup-strategy
*Статус:* Принято

*Контекст:* Защита от ransomware и случайного удаления.

*Решение:* Хранение неизменяемых резервных копий в S3-совместимом хранилище с WORM-политикой.

=== ADR-DES.INFRA.edge-region-failover-strategy
*Статус:* Принято

*Контекст:* Обеспечение доступности при отказе региона.

*Решение:* Multi-AZ развёртывание с geo-репликацией и автоматическим failover.

=== ADR-DES.INFRA.control-plane-isolation-strategy
*Статус:* Принято

*Контекст:* Изоляция управляющих компонентов от плоскости данных.

*Решение:* Support Metadata и Support DB размещаются в отдельном namespace/кластере.

== UI — Интерфейс пользователя

=== ADR-DES.UI.wcag-accessibility-strategy
*Статус:* Принято

*Контекст:* Обеспечение доступности для пользователей с ограниченными возможностями.

*Решение:* Соответствие WCAG 2.1 AA, обязательное для всех MVP-сценариев.

=== ADR-DES.UI.design-system-customization-strategy
*Статус:* Принято

*Контекст:* Белый лейбл для Enterprise-клиентов.

*Решение:* Темизация через CSS custom properties. Кастомизация логотипа, цветовой схемы, favicon через переменные themes.yaml.

=== ADR-DES.UI.data-loss-prevention-strategy
*Статус:* Принято

*Контекст:* Предотвращение потери несохранённых данных при сбоях.

*Решение:* Confirm-диалоги перед необратимыми операциями, автосохранение черновиков в localStorage, отмена через Ctrl+Z.

=== ADR-DES.UI.dangerous-actions-recovery-strategy
*Статус:* Принято

*Контекст:* Восстановление после опасных действий (удаление, массовые изменения).

*Решение:* Подтверждение для массовых операций, Soft-delete с archive=true, история изменений с возможностью отката.

=== ADR-DES.UI.version-context-visibility-strategy
*Статус:* Принято

*Контекст:* Отображение информации о текущей ветке и коммите в интерфейсе.

*Решение:* Индикатор текущей ветки в шапке редактора. Изменения отмечаются визуально до коммита.

=== ADR-DES.UI.error-feedback-strategy
*Статус:* Принято

*Контекст:* Понятные сообщения об ошибках для пользователя.

*Решение:* Человекочитаемые сообщения на русском языке. Возможность копировать технические детали (trace_id). Кнопка «Повторить» для временных ошибок.

=== ADR-DES.UI.degraded-mode-ux-strategy
*Статус:* Принято

*Контекст:* Поведение UI при отказе части сервисов.

*Решение:* Отображение баннера о деградации с указанием затронутых функций. Блокировка только пострадавших операций.

== API — Интерфейсы программирования

=== ADR-DES.API.rest-vs-graphql-vs-grpc
*Статус:* Принято

*Контекст:* Выбор протоколов для внешнего и внутреннего API.

*Решение:*
- gRPC — внутренние вызовы между микросервисами
- REST (JSON) — внешний API для отраслевых приложений
- WebSocket — realtime коллаборация
- GraphQL — опционально для фронтенда

=== ADR-DES.API.graphql-for-frontend
*Статус:* Принято

*Контекст:* Оптимизация запросов фронтенда к графу онтологии.

*Решение:* GraphQL как основной API фронтенда для навигации по графу. Динамические свойства через `propertyValues`, `outgoingEdges`, `incomingEdges`.

=== ADR-IMPL.API.rest-vs-grpc-for-sparql
*Статус:* Принято

*Контекст:* Выбор протокола для SPARQL endpoint.

*Решение:* SPARQL endpoint через REST с параметризованными запросами.

=== ADR-DES.API.bounded-context-scope
*Статус:* Принято

*Контекст:* Определение границ микросервисов.

*Решение:* Каждый микросервис владеет своим bounded context. API Gateway — единственный внешний интерфейс.

== DATA — Данные

=== ADR-IMPL.DATA.postgres-vs-mysql-for-version-store
*Статус:* Принято

*Контекст:* Выбор СУБД для Version Store.

*Решение:* PostgreSQL + JSONB для хранения дельт коммитов. JSONB обеспечивает индексацию и транзакционность.

=== ADR-DES.DATA.consistency-vs-availability-tradeoff
*Статус:* Принято

*Контекст:* Баланс между согласованностью и доступностью.

*Решение:* Strong consistency для операций записи (Neo4j, PostgreSQL), eventual consistency для кэша (Redis) и очередей (RabbitMQ).

=== ADR-DES.DATA.cache-strategy
*Статус:* Принято

*Контекст:* Стратегия кэширования для производительности.

*Решение:* Redis Cluster для кэша часто запрашиваемых узлов и распределённых блокировок. Write-through для онтологий, TTL-based для метрик.

=== ADR-IMPL.DATA.neo4j-vs-graphdb
*Статус:* Принято

*Контекст:* Выбор Triple Store.

*Решение:* Neo4j как primary Triple Store. GraphDB — опционально для RDF-нативных сценариев.

== PROCESS — Процессы

=== ADR-DES.PROCESS.monolith-to-microservices-evolution
*Статус:* Принято

*Контекст:* Переход от прототипа к микросервисам.

*Решение:* Микросервисы с первого дня. Выделение Ontology Service и Versioning Service как независимых сервисов на Rust.

== SECURITY — Безопасность

=== ADR-DES.SECURITY.sparql-injection-prevention-strategy
*Статус:* Принято

*Контекст:* Защита от SPARQL-инъекций.

*Решение:* Параметризованные запросы, строгое экранирование, read-only endpoint (`/api/v1/sparql`).

=== ADR-DES.SECURITY.rbac-authorization-strategy
*Статус:* Принято

*Контекст:* Модель управления доступом.

*Решение:* Иерархическая RBAC (Owner → Maintainer → Viewer) с наследованием прав по цепочке Group → Ontology.

=== ADR-DES.SECURITY.oauth-identity-provider-selection
*Статус:* Принято

*Контекст:* Выбор Identity Provider.

*Решение:* Keycloak с поддержкой OAuth2 / OIDC. Поддержка российских провайдеров (ЕСИА, Яндекс, VK) и Google.

=== ADR-IMPL.SECURITY.secrets-management-strategy
*Статус:* Принято

*Контекст:* Управление секретами.

*Решение:* Все секреты — через Helm values / Kubernetes Secrets. Никаких секретов в коде или .env-файлах в репозитории. Валидация через pre-commit hook.

=== ADR-DES.SECURITY.dependency-security-strategy
*Статус:* Принято

*Контекст:* Управление уязвимостями зависимостей.

*Решение:* SCA-сканирование (Trivy), автоматические обновления через Renovate/Dependabot, SBOM в формате SPDX.

=== ADR-DES.SECURITY.backup-encryption-strategy
*Статус:* Принято

*Контекст:* Шифрование резервных копий.

*Решение:* AES-256-GCM шифрование бэкапов на стороне клиента. Ключи — в Kubernetes Secrets. Verify после создания.

=== ADR-DES.SECURITY.api-security-gates-strategy
*Статус:* Принято

*Контекст:* Безопасность API.

*Решение:* OWASP ASVS Level 2 как обязательный стандарт. SAST (Semgrep), DAST, BOLA/BFLA-тестирование.

== IMPL — Реализация

=== ADR-IMPL.STACK.postgres-vs-mysql
*Статус:* Принято

*Контекст:* Выбор реляционной СУБД.

*Решение:* PostgreSQL с JSONB для Version Store.

=== ADR-IMPL.STACK.rust-for-core-services
*Статус:* Принято

*Контекст:* Выбор языка для высоконагруженных компонентов.

*Решение:* Rust для Ontology Service и Versioning Service. Максимальная производительность, безопасность памяти, отсутствие GC.

=== ADR-IMPL.STACK.go-for-auth-service
*Статус:* Принято

*Контекст:* Выбор языка для Auth Service.

*Решение:* Go. Встроенная конкурентность (goroutines), статический бинарник, простота gRPC-серверов.

=== ADR-IMPL.STACK.python-for-metrics-and-notifications
*Статус:* Принято

*Контекст:* Выбор языка для аналитических сервисов.

*Решение:* Python. Быстрая разработка, богатая экосистема (pandas, numpy, aio-pika).

=== ADR-IMPL.STACK.vue3-for-frontend
*Статус:* Принято

*Контекст:* Выбор фронтенд-фреймворка.

*Решение:* Vue 3 + Composition API + TypeScript + Vite + pnpm + Vue Flow.

=== ADR-IMPL.DATA.antora-bundled-documentation
*Статус:* Принято

*Контекст:* Инструмент для документации.

*Решение:* Antora для сборки проектной и пользовательской документации.

== BIZ — Бизнес

=== ADR-BIZ.SECURITY.gdpr-mandate
*Статус:* Принято

*Контекст:* Соответствие GDPR и 152-ФЗ.

*Решение:* Data residency, право на забвение, журнал аудита доступа к данным, согласие на обработку ПДн.
