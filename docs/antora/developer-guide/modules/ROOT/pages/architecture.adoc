= Architecture
:description: Microservices structure, service inventory, and communication patterns.

== Overview

VEDO Core uses a *microservices architecture* organized as a monorepo. 14+ loosely coupled, independently deployable services — each owning its data, communicating through well-defined APIs (REST/gRPC/events), and scalable independently.

The architecture was chosen because the project requires polyglot persistence (Neo4j, PostgreSQL, Redis), different scaling profiles per service (ontology queries need more CPU than auth), and independent team ownership across Go, Rust, Python, and TypeScript codebases.

== Key Patterns

* **gRPC** for inter-service communication, REST for external API, WebSocket for real-time
* **Structured logging** with OpenTelemetry trace context propagation across all services
* **Health check endpoints** (`/health`, `/ready`) on every service
* **Multi-stage Docker builds** (Go: golang→alpine, Rust: rust→debian-slim, Python: python-slim, TS: node→nginx)

== Key Principles

. *Service Autonomy* — each service owns its data, runtime, and deployment.
. *API-First Contracts* — interfaces defined as contracts before implementation.
. *Smart Endpoints, Dumb Pipes* — business logic lives inside services; the gateway routes but does not orchestrate.
. *Design for Failure* — circuit breakers, retries with backoff, timeouts, fallback strategies at the gateway level.
. *Polyglot Persistence* — Neo4j for graphs, PostgreSQL for version history, Redis for caching/locks.
. *Observability by Default* — OpenTelemetry trace context propagated through all services; structured JSON logging with `trace_id` and `request_id`.

== Anti-Patterns to Avoid

[cols="1,4"]
|===
|❌ *Distributed Monolith* |Services coupled via synchronous calls requiring coordinated deploys
|❌ *Shared Database* |Multiple services accessing the same Neo4j/PostgreSQL tables
|❌ *Nano-services* |Services too small that operational overhead exceeds business value
|❌ *Leaky Gateway* |API Gateway containing business logic instead of routing
|===

== Write-Path Invariant

*Architectural constraint* per `ADR-DES.API.write-path-invariant` (specs/adr/): *no path to mutate ontology state exists outside the versioning pipeline.*

* **No direct writes to Neo4j** — neither humans, nor AI agents, nor administrators write to ontology storage directly. The prohibition covers both ABox and TBox.
* **Every mutation** follows the pipeline `branch → commit → MR → review → merge` and is a logged commit with an audit trail (who, what, when, branch).
* **REST write endpoints** operate on branch-local snapshots, never on the live ontology.
* **Enforcement** is deferred to M10 (MR workflow becomes the enforcement backbone).
* **Current code** carries deprecation warnings on the legacy direct-write surface and is annotated for migration.

Source requirement: `REQ-CON.SECURITY.write-path-invariant` (specs/requirements/).

== REST API Structure

The REST API follows GitLab-aligned conventions per `ADR-DES.API.rest-gitlab-alignment` (specs/adr/): operations are nested under `/projects/{pid}/`.

|===
|Area |Current state |Target state

|Ontology content |`/api/v1/ontologies/*` (deprecated) |`/projects/{pid}/repository/classes|properties|individuals` with `?ref=`
|Versioning |`/api/v1/versioning/*` |`/projects/{pid}/repository/commits|branches`
|Merge Requests |— |`/projects/{pid}/merge_requests` (iid-based, PUT merge, state_event, /diffs)
|Releases |— |`/projects/{pid}/releases`
|Branch protection |— |`/projects/{pid}/protected_branches`
|===

* Legacy paths `/api/v1/ontologies/*` return `Deprecation: true` + `Sunset` headers and remain active until the REST API GitLab Alignment Migration (M10/M11, see `feature-rest-api-realignment-adrs.md`).
* Planned endpoints (`/releases`, `/merge_requests`, `/protected_branches`) return `501 Not Implemented` with the `x-vedo-status: planned` header — a contract stub for consumers and test authors.
* Global endpoints are read-aggregations only.

Source requirement: `REQ-FUN.API.rest-gitlab-alignment` (specs/requirements/).

== Publishing Model

The publishing model extends the original ontology-publishing decision per `ADR-DES.INFRA.publishing-extension` (specs/adr/) with CQRS and a binary access model.

* **CQRS serving layer** — a published snapshot (release) is a materialized read-only view of the ontology at a specific commit, served from a separate read-only store (second Neo4j or MinIO+index; decision deferred to implementation).
* **Binary visibility** — public (no auth, basic DoS protection) or restricted (API key via `X-VEDO-API-Key`).
* **Maintainer gate** — the publish action requires role weight ≥ 2 (Maintainer+); there is no separate publisher role.
* **Releases naming** — published snapshots are exposed as `/projects/{pid}/releases`.

Source requirement: `REQ-CON.STACK.publishing-extension` (specs/requirements/).

NOTE: Code migration to the target architecture is deferred to M10 (MR workflow) and M11 (publishing pipeline). Current code includes deprecation warnings and planned stubs per the ADRs above.
