= API Reference
:description: REST and GraphQL endpoints exposed through the API Gateway.

== Base URL

[source]
----
http://localhost:8080          # API Gateway (development)
https://api.vedo-core.example  # Production
----

All external requests go through the API Gateway. The frontend never accesses backend services directly.

== Organization & Access Control

Organizational model endpoints for group hierarchy, project catalog, membership management, visibility, and access policies.

=== Groups

|===
|Method |Path |Description

|`GET` |`/api/v1/groups` |List groups (paginated, searchable)
|`POST` |`/api/v1/groups` |Create a group (Owner, idempotent)
|`GET` |`/api/v1/groups/{id}` |Get group details
|`PUT` |`/api/v1/groups/{id}` |Update group (Owner, idempotent)
|`DELETE` |`/api/v1/groups/{id}` |Delete group (Owner, must be empty)
|`GET` |`/api/v1/groups/{id}/subgroups` |List child groups
|`GET` |`/api/v1/groups/{id}/members` |List group members
|===

=== Projects

=== Visibility

|===
|Method |Path |Description

|`GET` |`/api/v1/ontologies/{id}/visibility` |Get visibility level
|`PUT` |`/api/v1/ontologies/{id}/visibility` |Set visibility (Owner, idempotent)
|===

=== Access Policies

|===
|Method |Path |Description

|`GET` |`/api/v1/ontologies/{id}/policies` |List ABAC policies
|`POST` |`/api/v1/ontologies/{id}/policies` |Create policy (Owner, idempotent)
|`DELETE` |`/api/v1/ontologies/{id}/policies/{policyId}` |Delete policy (Owner, idempotent)
|===

Role values: `Guest`, `Reporter`, `Developer`, `Maintainer`, `Owner`. Legacy `Viewer`/`Editor` aliases accepted for backward compatibility.

Visibility values: `private`, `internal`, `public`. Private requires explicit membership; internal allows any authenticated org member; public allows anonymous read access.

Write endpoints support `Idempotency-Key` header (UUID). Membership endpoints require it (400 if missing).

== GraphQL

The frontend uses Apollo Client to query the API Gateway's GraphQL endpoint for complex data operations:

[source,graphql]
----
query GetOntology($id: ID!) {
  ontology(id: $id) {
    id
    name
    description
    classes {
      id
      label
      properties { name type }
    }
    relationships {
      from
      to
      type
    }
  }
}
----

== Error Codes

|===
|HTTP Status |Error Code |Description

|400 |`BAD_REQUEST` |Malformed request body or parameters
|401 |`UNAUTHORIZED` |Missing or invalid authentication token
|403 |`FORBIDDEN` |Insufficient permissions (RBAC)
|404 |`NOT_FOUND` |Resource does not exist
|405 |`METHOD_NOT_ALLOWED` |HTTP method not supported on this endpoint
|409 |`CONFLICT` |Version conflict or duplicate resource
|422 |`UNPROCESSABLE_ENTITY` |Semantic validation failure
|429 |`RATE_LIMITED` |Rate limit exceeded
|500 |`INTERNAL_ERROR` |Unhandled server error
|===

Error responses follow a consistent JSON shape:

[source,json]
----
{
  "error": "NOT_FOUND",
  "message": "Ontology with id 'abc123' was not found",
  "trace_id": "a1b2c3d4-e5f6"
}
----

== Security

* *BOLA/BFLA enforcement* at the API Gateway level — object-level and function-level authorization checks prevent unauthorized access.
* *Negative authorization tests* are part of the test suite (`tests/security/`).
* *SAST/DAST security gates* run in CI alongside dependency scanning.

See xref:authentication.adoc[Authentication] for token flow and identity providers.
