= Organizational Model
:author: VEDO Core Team
:revnumber: 0.2.0
:description: Multi-team organization model with group hierarchy, project catalog, role-based membership, and visibility levels.

== Overview

The organizational model provides GitLab-like group hierarchy and project catalog for multi-tenant ontology management. It replaces the Apollo GraphQL test fixtures with a real backend backed by PostgreSQL.

Architecture: `auth-service` owns org data (PostgreSQL), exposes gRPC API. `api-gateway` proxies REST/GraphQL to auth-service gRPC.

== Key Concepts

* Group: hierarchical scope node (type=group) with parent-child relationships
* Project: scope node (type=project) under a group; the unit of access, versioning, and membership
* Ontology: graph content of a Project (TBox/ABox, classes, properties, individuals). Ratio 1:1 with Project — one Project contains exactly one Ontology
* Membership: role assignment (user_id + scope + role) — stored on Project, inherited by the paired Ontology
* Visibility: Private | Internal | Public per Project (applies to the paired Ontology via 1:1)
* Inheritance: memberships propagate from parent to child (max-role-wins)
* Max Role Wins: highest role across inherited and direct memberships

See xref:project-ontology-model.adoc[Project ↔ Ontology Model] for the dedicated explanation of the 1:1 invariant and the responsibility split between Project (workspace) and Ontology (graph content).

== Role Hierarchy

[cols="1,2,1"]
|===
| MVP Role | Priority | Legacy Alias
| Guest | 1 | Viewer (mapped as alias)
| Reporter | 2 | —
| Developer | 3 | Editor (mapped as alias)
| Maintainer | 4 | Maintainer
| Owner | 9 | Owner
|===

Legacy roles `Viewer` and `Editor` are accepted as backward-compatible aliases for `Guest` and `Developer` respectively. Enterprise/ops roles (`SupportEngineer`, `SRE`, `SecurityLead`, `ProductOwner`) exist in the data model but are outside the MVP happy path.

Only Owners can manage memberships, change visibility, and manage policies. Permission inheritance follows max-role-wins: the highest role across direct and inherited memberships determines effective permissions.

== Group Hierarchy

Groups can be nested up to 5 levels deep. Creating or moving a group beyond this limit returns a `HIERARCHY_DEPTH_EXCEEDED` validation error.

== Project Movement

A project can be moved from one group to another. Moving a project updates effective membership and inherited roles for all members based on the new parent group. The paired Ontology moves with the Project (1:1 invariant). Authorization caches for the affected scopes are invalidated on move.

== PostgreSQL Schema

The `vedo_org` database contains four tables:

* `scopes` — group/project hierarchy nodes with visibility + tenant isolation. After migration 007, `type='project'` replaces the legacy `type='ontology'`.
* `ontologies` — 1:1 content rows paired with project scopes (migration 008). Each row references its Project via a foreign key and carries the ontology-level metadata (label, description, IRI).
* `memberships` — role assignments with UNIQUE(scope, user_id) and CHECK constraint validating role enum
* `attribute_policies` — ABAC policy definitions (JSONB pattern)
* `audit_events` — authorization audit trail (event, reason, user_id, object_type, object_id, source_ip, trace_id)

Migrations: `src/services/auth-service/migrations/` (001-009). Migrations 007-009 are part of the Project ↔ Ontology separation:

* 007 — rename `scopes.type='ontology'` to `scopes.type='project'`
* 008 — create the `ontologies` table with FK to the project scope (preserves the 1:1 invariant)
* 009 — backfill `ontologies` rows from legacy `type='ontology'` scopes (runs before the type rename)

Migration 006 adds MVP role vocabulary (`Guest`, `Reporter`, `Developer`, `Maintainer`, `Owner`) to the memberships CHECK constraint while preserving legacy roles (`Viewer`, `Editor`) as backward-compatible aliases.

== Project Lifecycle

Projects follow a simple lifecycle:

* *Create* — a new Project is created inside a Group with a paired Ontology (1:1).
* *Fork* — copy a Project (with its Ontology) into the user's workspace. See <<Fork Model>> below.
* *(post-MVP)* Merge upstream — incorporate changes from the source Project into the fork.

=== Fork Model

Forking creates a copy of a Project (with its paired Ontology) linked to the source via `upstream_project_id`. The fork is private by default; the user becomes Owner of the new Project.

Fork mechanics:

* *Endpoint:* `POST /api/v1/projects/{id}/fork`
* *Request body:* empty (`Idempotency-Key` header required)
* *Response:* `201 Created` with `{project_id, ontology_id, upstream_project_id}`
* *RBAC:* any user with read access to the source Project can fork. Guest role can fork public/internal projects.
* *Saga:* creates Project scope → paired Ontology → copies main branch via Versioning Service gRPC → emits `project.forked` audit event. On failure, compensating action deletes the new Project + Ontology.
* *Idempotency:* `Idempotency-Key` header required (same as other write endpoints).

=== `upstream_project_id` field

The `upstream_project_id` field on Project (`scopes` table) is nullable:

* When non-null: this Project is a fork of the referenced upstream Project.
* When null: this is an original (non-forked) Project.

Database constraints:

* `ON DELETE SET NULL` — when the upstream Project is deleted, the fork remains as an orphan (consistent with the Git model).
* Partial index: `idx_scopes_upstream` on `upstream_project_id WHERE upstream_project_id IS NOT NULL`.

== Audit Events

Structured audit events are emitted for the following organizational lifecycle operations:

* Group create, delete, move
* Project create, delete, move, fork
* Member add, remove, role change

Each audit event includes:

* `event` — operation name
* `reason` — reason or authorization context
* `user_id` — acting user
* `object_type`, `object_id` — target scope
* `source_ip` — request origin
* `trace_id` — OpenTelemetry trace correlation
* `timestamp` — event time

Audit events are persisted in the `audit_events` table and logged as structured JSON via `slog` at INFO/WARN level. Tokens, secrets, and PII beyond stable user/scope identifiers are excluded.

== REST API Endpoints

All endpoints require `Authorization: Bearer <JWT>` header.

=== Groups

* `GET /api/v1/groups` — list all groups
* `POST /api/v1/groups` — create group (Owner)
* `GET /api/v1/groups/:id` — get group details
* `PUT /api/v1/groups/:id` — update group (Owner)
* `DELETE /api/v1/groups/:id` — delete group (Owner, must be empty)
* `GET /api/v1/groups/:id/subgroups` — list child groups
* `GET /api/v1/groups/:id/members` — list group members

=== Projects

* `GET /api/v1/projects` — list projects (paginated, searchable)
* `POST /api/v1/projects` — create project (Owner)
* `GET /api/v1/projects/:id` — get project details (includes `ontology_id` for the 1:1 paired Ontology)
* `PUT /api/v1/projects/:id` — update project (Owner)
* `DELETE /api/v1/projects/:id` — delete project (Owner; cascades to the paired Ontology)

=== Members

Members live on Project (not Ontology), matching GitLab `/projects/:id/members`.

* `GET /api/v1/projects/:id/members` — list project members
* `POST /api/v1/projects/:id/members` — add member (Owner)
* `PUT /api/v1/projects/:id/members/:userId` — update role (Owner)
* `DELETE /api/v1/projects/:id/members/:userId` — remove member (Owner)

=== Visibility

Visibility is a Project attribute; the paired Ontology inherits it via the 1:1 link.

* `GET /api/v1/projects/:id/visibility` — get visibility
* `PUT /api/v1/projects/:id/visibility` — set visibility (Owner)

=== Access Policies

ABAC policies live on Project.

* `GET /api/v1/projects/:id/policies` — list policies
* `POST /api/v1/projects/:id/policies` — create policy (Owner)
* `DELETE /api/v1/projects/:id/policies/:policyId` — delete policy (Owner)

See xref:integrator-guide:api-reference.adoc[] for the full REST contract and ADR-DES.API.organization-rest-endpoints for the canonical endpoint list.

== Idempotency

All write endpoints support `Idempotency-Key` header (REQ-FUN.API.write-idempotency).

* Same key + same body: returns cached response
* Same key + different body: 409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_PAYLOAD
* Missing key on membership endpoints: 400 INVALID_IDEMPOTENCY_KEY
* TTL: 24 hours (Redis or in-memory storage)
